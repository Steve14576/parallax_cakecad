## 1. 项目一句话定义

CakeCAD 是一个以时间为主轴的开放式物质过程 CAD/PLM 工具。

它允许用户像在 Rhino/Blender 中一样自由摆放、命名、画形状，像在 PR/FL Studio 中一样用时间线观察对象和关系的出现、消失、绑定、解绑和分支，又像 PLM 一样追踪物料来源、批次、版本和历史；当用户需要分析时，系统才把相关局部现场编译成可计算的算例。

更短的产品哲学：

> 时间是坐标系，对象和关系是事实，轨道是视图，分析是临时解释。

英文口号候选：

> Time is the coordinate system; objects and relations are the facts; tracks are views; analysis is a temporary interpretation.

## 2. 它不是什么

CakeCAD 需要先通过排除法保持清醒。

### 2.1 不是菜谱游戏

CakeCAD 不预设“牛肉只能被炒”“面皮只能被擀”“工具只能服务某个固定食材”。食材、工具、容器、设备都不预设命运。

一个对象叫牛肉，并不意味着它只能进入 `炒牛肉`。它可以被切、腌、真空封装、烤、煎、风干、放在一旁、作为实验对象、丢弃或重新利用。

### 2.2 不是 Creo/SolidWorks 式强约束特征树

CakeCAD 不要求每一步先定义完整草图、完整约束、完整根依赖，然后才允许下一步。

它允许：

- 先画；
- 先写；
- 先放；
- 先命名；
- 以后再补语义；
- 历史暂时悬空；
- 物料暂时不守恒；
- 空间和物料关系暂时不同步。

系统不应在用户探索早期就要求用户签署一份完整物理世界公约。

### 2.3 不是 Blender 的食品版

3D 很重要，但 3D 不是全部。CakeCAD 的核心不是“捏出漂亮食物模型”，而是记录、理解和分析食物作为物质过程的历史。

### 2.4 不是 ANSYS/COMSOL 的食品版

CakeCAD 不默认实时求解热、流、应力、碰撞、水分扩散和化学变化。仿真只在具体问题出现时局部启动。

用户可以做出悬空、穿模、不守恒、不完整来源的东西；只要不拿它去做严格分析，系统不应阻止。

### 2.5 不是普通菜谱 App

CakeCAD 不以搜索、推荐、收藏和阅读菜谱为中心。Markdown 笔记可以存在，但它不是全部。

### 2.6 不是通用节点平台

CakeCAD 可以在深层拥有图结构、数据管线或节点视图，也可以按需展开这些视图；但产品目标不是提供一个任意节点、任意插件、任意工作流的通用图编程平台。

节点/图如果出现，应服务于 CakeCAD 的对象、关系、时间、物料、分析和溯源，而不是反过来让项目变成抽象图平台。

## 3. 根原则

### 3.1 开放世界，而不是封闭世界

系统没定义的东西，仍然可以存在；只是不能参与某些严格计算。

例如：

- 杏仁粉可以先存在，即使物性未知。
- 一个对象可以先叫“月饼”，即使它的上游没有定义。
- 一个空间里可以先摆出蒸馏装置，即使它还没有被验证为可运行设备。

正式原则：

> 未知不等于不存在；未定义不等于错误；不可分析不等于不可编辑。

### 3.2 局部闭合，而不是全局闭合

用户不需要让整个项目都完整。用户只需要让当前任务相关的一小块达到可用闭合。

- 为了看 3D：几何闭合即可。
- 为了查来源：对象关系闭合即可。
- 为了算烘烤：厚度、温度、材料视图闭合即可。
- 为了导出制造路径：路径与设备约束闭合即可。

这叫“局部可计算闭合”。系统不应为了一个局部分析，强迫整个项目都变成全局可计算。

### 3.3 软类型，而不是无类型

对象可以先只有名字，但类型和角色可以渐进附加。

例如“杏仁粉”可以逐步获得：

- 物料角色：干粉；
- 工艺角色：提供颗粒感和香气；
- 分析角色：热模型中的固体填料；
- PLM 角色：某批次原料；
- 几何角色：无独立形状，或以粉堆/容器内容显示。

类型不是一次性永久判决，而是随任务增加的角色集合。

### 3.4 事实、解释、假设和预测必须分开

同一对象周围可能同时存在：

- Fact：实际称量 487g；
- Observation：表面偏湿；
- Interpretation：可能因为碗壁残留导致差额；
- Hypothesis：如果再多搅拌 2 分钟也许能恢复；
- Prediction：若加 20g 柠檬汁，乳化风险升高；
- Decision：本次仍按当前配方继续。

它们不能混进同一个字段。尤其是预测不能覆盖实测，解释不能冒充事实。

### 3.5 容错式创作

用户可以构建失败的、悬空的、缺失的、不守恒的项目。

系统的职责不是消灭这些状态，而是知道：

- 当前为什么不能执行；
- 当前为什么不能分析；
- 哪些关系是断的；
- 哪些值是手填的；
- 哪些依赖已经过期；
- 用户需要怎样才能让局部闭合。

### 3.6 操作自由，仿真诚实

用户可以在创作层面随便摆、随便写、随便命名、随便跳步。系统可以提示，但不要轻易阻止。

但一旦用户要求分析、仿真、导出、计算或制造，系统必须诚实：

- 不足的输入要标出来；
- 无效的关系要标出来；
- 证据来源和有效范围要标出来；
- 模型不能假装知道它不知道的东西。

## 4. 基本事实模型

本节只定义概念，不定义代码类、数据库表或序列化格式。

### 4.1 Project

Project 是一个 CakeCAD 工作文件的整体容器。它包含笔记、对象、事件、关系、时间、分支、测量、分析结果和导出物。

### 4.2 Note

Note 是自由研发记录，通常可以是 Markdown。

Note 可以包含：

- 半句话；
- 猜测；
- 错误；
- 情绪；
- 动机；
- 注释；
- 未来计划；
- 互相冲突的想法。

Note 不默认是可执行程序。系统可以识别候选锚点，但不能把 Note 中的一切自动当作事实。

Markdown 是自由底稿区，不包含 CakeCAD 脚本，也不因使用了特定词语而自动提交对象、物料或过程事实。Markdown 可以插入指向时间轨道、对象、事件、分支或分析结果的定位书签；书签只负责导航和引用，不把周围文字提升为正式事实。

### 4.3 Object

Object 是一个有身份、可以被引用的东西。

Object 可以是：

- 食材；
- 半成品；
- 成品；
- 容器；
- 工具；
- 设备；
- 临时组合体；
- 变量承载物；
- 被用户命名但暂未解释完整的对象。

容器、工具和设备也是 Object，不应被硬塞进“用某工具处理某食物”的固定语法。

Object 的身份应能跨时间存在；对象消失在当前视图中，不等于从历史中删除。

对象在何时获得“面糊”“果酱”“成品”等身份，默认由用户命名或确认，而不是由系统根据配比、空间或过程自动裁决。模型可以提出候选解释，但不能替用户悄悄改变对象身份。

对象身份与物料状态默认按以下规则处理：

- 一进一出的连续处理默认保留同一对象身份，并记录随时间变化的状态、名称和角色。例如生曲奇经过烘烤成为熟曲奇，是同一块曲奇经历烘烤过程，而不是生曲奇退场、熟曲奇凭空入场。
- 一分多的分件默认创建新的子对象身份，原对象保留在历史中，并记录它在分件时被消耗、分配或终止整体身份。
- 多进一的真正混合或融合，在用户需要把结果独立命名、流转、分析或追溯时创建新的结果对象；各输入仍保留历史。
- 仅仅共处一只碗、空间接触、堆叠或装配，不自动创建新物料对象。它们可以先由关系表达。
- 用户可以覆盖默认判据。例如某次化学转化需要把产物视为新对象，或某个组合体需要整体身份；系统记录该决定而不宣称存在唯一客观本体。

因此，对象 ID 表示可追踪的连续性，状态与名称可以沿时间变化；新 ID 主要用于数量分叉、来源汇合和用户明确要求独立身份的场景。

### 4.4 Event

Event 是某个时间发生的变化或记录。

Event 可以是：

- 搬移；
- 加入；
- 倒出；
- 混合；
- 命名；
- 测量；
- 观察；
- 检查；
- 暂停；
- 换料；
- 绑定来源；
- 启动分析。

Event 不一定是烹饪动作。一个“检查气密性”的 3D 浮动文字，也可以是有时间、有空间锚点、无物料效应的事件。

### 4.5 Relation

Relation 是对象之间在某个时间范围内成立的联系。

例如：

- located_in：饼干碎在碗中；
- supported_by：面皮由油纸支撑；
- connected_to：冷凝管连接烧瓶；
- derived_from：曲奇面团来自面粉、糖、黄油和蛋；
- conforms_to：面皮贴合派盘；
- heated_by：烧瓶被酒精灯加热；
- contains：容器包含某些物料。

Relation 必须能带有效期。冷凝器连接蒸馏头只在装配期间成立；面皮在油纸上只在揭下之前成立。

### 4.6 Time Segment

Time Segment 是对象、关系、事件或状态在时间中的有效片段。

时间不只有精确时间。CakeCAD 至少需要支持：

- 精确区间：10:00–10:03；
- 模糊范围：大约 10–20 分钟；
- 先后关系：after mixing；
- 未知时间：尚未记录；
- 开放结束：直到表面凝固。

轨道上的线段主要表示“对象或关系在时间中的有效片段”，不是所有线段都是操作。

### 4.7 Region

Region 是有名字、有范围、可选有语义的空间标记。

例如：

- 仓库区；
- 备料区；
- 台面 A；
- 烤箱旁；
- 当前工作区。

Region 不是默认 Object。它通常不参与物料账本，不需要复杂生命周期管理，可以随手画、随手删。

当 Region 需要参与分析或过程事实时，可以被提升为 Object。例如台面温度影响巧克力回温时，台面不再只是区域，而可能成为有属性的对象。

### 4.8 Pile

Pile 是轻量的、位置化的物料聚集，用来表示“桌上一坨东西”。

Pile 有位置、范围和内容物，但没有容器壁、容量、清洗状态。

不要默认给所有散装物料分配容器。物料出现时可以有三种形态：

- 在容器中；
- 以 Pile 形式散装；
- 暂未决定，只是库存或抽象态。

### 4.9 Stub

Stub 是被声明存在但不展开建模的供给、支撑、边界条件或辅助系统。

例如：

- 冷凝管“隔空通冷凝水”；
- 某处有支架支撑但不画支架；
- 烤箱已预热；
- 派盘刷油层作为界面条件；
- 油纸提供防粘功能。

Stub 表达的是：“我知道这里需要什么，但它不是今天要展开建模的问题。”

Stub 可以从纯视觉占位，逐步升级为带参数的分析输入。

### 4.10 Value 与 Variable

Value 是某个量的当前值、来源、单位和状态。Variable 是可被表达式、分析模型或经验公式引用的量。

Variable 可以来自：

- 对象属性：烧瓶容量、柠檬皮质量；
- 测量值：30 分钟后得到 5g 精油；
- 自由变量：提取效率；
- 表达式结果：产率、成熟度、风险值。

Variable 是 PLM 和 CAE 之间的重要桥梁：同一个 5g 既可以是一次实测事实，也可以成为经验公式的拟合点。

### 4.11 Measurement

Measurement 是实测记录。它比预测、解释和默认派生值更硬。

原则：测量不能被模型覆盖。上游修改导致测量依赖过期时，系统应提示冲突或断点，而不是静默改写测量值。

### 4.12 Branch

Branch 是项目历史中的一个变体。

当前原则：分支创建时不要求用户先选择类型。用户可以先分支，之后系统根据内容或用户命名显示标签。

分支可用于：

- 备份；
- 设计变体；
- 反事实情景；
- 破坏性分析；
- 实际执行记录；
- 校准实验。

但这些是用途标签，不应成为创建分支前的强制分类。

### 4.13 Lock

Lock 是自动传播不能静默越过的边界。

Lock 可以来自：

- 用户手动固定；
- 实测值；
- 已执行事实；
- 外部设备导入；
- 已发布版本；
- 分析算例输入。

用户仍可手动修改 Lock，但系统不能自动悄悄改。

### 4.14 Analysis Case 与 Analysis Result

Analysis Case 是一次局部分析的输入、问题、模型和作用域。Analysis Result 是该分析的输出、证据、有效范围和依赖。

分析不是全局物理引擎。分析读取当前事实，建立局部算例：

- 非破坏性分析只保存结果；
- 会改变事实或需要破坏主线一致性的分析应进入分支；
- 分析结果绑定到版本、时间范围和依赖输入。

### 4.15 Conflict

Conflict 是系统知道“这里不一致、过期、断裂或不可分析”的记录。

Conflict 不等于错误。它可以是可接受的草图状态，也可以是需要用户确认的调和对象。

## 5. 空间、物料与过程的提交规则

一个空间动作可能只改变位置，也可能进一步改变物料归属、质量流、过程状态或分析意义。

因此空间编辑默认只生成草图事件；只有用户确认、模板操作、明确命令或分析需要时，才提升为物料事实或过程事实。

### 5.1 影响维度

一个现场事件可以拆成多个影响维度：

- spatialEffect：空间效果；
- materialEffect：物料效果；
- processEffect：过程效果；
- stateEffect：状态效果。

同一个动作不必四者同时成立。

例如搬橙子：空间变化成立，物料和过程可以无变化。

例如给泡芙挤奶油：空间路径成立，是否发生物料转移、转移多少、泡芙是否成为填充成品，都可以后续确认。

### 5.2 提交状态

一个影响可以处于不同提交状态：

- sketch：草图，只是摆放或设想；
- declared：用户声明这件事有某种意义；
- committed：进入正式物料/过程事实；
- measured：由测量或实际执行确认。

这些名称仍可调整，但分层是必要的。

### 5.3 工作面与事实权威

CakeCAD 的正式设计/PLM 事实不在 CAE 层。CAE 只读取事实并产生带来源的分析解释。正式事实存于共享的项目事实底座，工作区、DAW 轨道、节点图和 CMD 都只是读取或修改同一底座的交互入口。

各工作面的职责如下：

- Markdown：自由底稿，只提供书签和引用，不提交事实。
- DAW 轨道：时间化事实的主要浏览与编辑入口，可以新建对象、拖动时间、改变存在区间、建立关系和记录操作。
- 工作区：直接操纵入口；基础空间摆放和建模可以提交设计/PLM 事实，但具体建模能力是否首版实现仍待原型验证。
- 节点图：DAW 所表达事实的另一种结构视图，或某些数据管道的深层视图；不是另一份独立数据。
- CMD：对标 CAD 的命令入口。既支持先选择对象再输入动词，也支持先输入命令动词再选择一个或多个对象。
- CAE/分析：读取已选事实并生成结果、建议、预测或候选情景，不拥有改写历史事实的更高权威。

多个入口发生修改时，不做“谁覆盖谁”的跨文档同步；它们都生成可追踪命令或事件，顺序写入同一历史。Markdown 文字与正式事实冲突时允许共存，因为 Markdown 本来就是底稿；系统只提示相关书签附近的事实可能已变化。

### 5.4 操作发起与确认模式

CakeCAD 不应把鼠标拖动到某处自动弹窗作为常态提交方式。空间直接操纵可以产生 sketch 状态，但正式物料、过程或关系事实通常通过以下模式之一确认：

- 先选择一个或多个对象，再打开右键菜单选择动作，最后选择目标；
- 先打开右键菜单选择动作，再依次点选参与对象；
- 先从工具栏激活一个工具，再点选一个或多个对象，Enter 或完成手势确认；
- 先在 CMD 输入命令动词，再点选对象或输入参数，Enter 确认；
- 先多选对象，再在 CMD 输入命令动词，Enter 确认。

前两类接近装配式上下文选择，后两类接近 CAD 命令式工作流。右键菜单同时提供通用动作和由对象角色决定的专门动作；工具栏和 CMD 提供相对稳定、可学习、可复用的通用动作。

命令语法遵循谓语与宾语分离：谓语独立注册（如“倒入”“分件”“命名”），宾语由用户在执行时通过点选、多选或参数提供；任何菜单不得把谓语与固定宾语绑死成组合项。右键、工具栏和 CMD 共享同一命令注册表。

详细的交互状态机、菜单分层、DAW 部件与命令词汇表见 `docs/specs/ux-interaction-model.md`，该文件是所有 UI 行为的直接上游；实现与本文件不一致时先改文档。

## 6. 两条一级主轨与视图系统

CakeCAD 需要时间轴，但不应照搬 DAW 本体。轨道不是独立数据源，而是同一事实底座的投影。

### 6.1 一级主轨 A：物料＆操作

它回答：

- 东西从哪里来；
- 经历了什么；
- 什么时候产生；
- 什么时候被消耗；
- 被分成了什么；
- 由哪些输入得到；
- 哪些测量、数量和来源绑定在其上。

子轨可以包括：

- 对象存在；
- 过程事件；
- 物料来源；
- 数量/流量；
- 状态变化；
- 测量；
- 分支差异。

### 6.2 一级主轨 B：物料＆位置

它回答：

- 东西在哪里；
- 放在哪个容器里；
- 和谁接触；
- 沿什么路径移动；
- 以什么为基准；
- 什么时候从这里移到那里。

子轨可以包括：

- 空间存在；
- 位置；
- 容器；
- 接触/包含；
- 工具作用；
- 设备连接；
- 路径/变形；
- 空间冲突。

### 6.3 旁挂视图

以下内容不属于一级主轨本体，但可以通过对象、事件、时间范围、分支和锚点连接：

- Markdown 笔记；
- 问题/意图；
- 分析算例；
- 分析结果；
- BOM；
- 证据；
- 导出文档。

### 6.4 轨道是投影，不是同步对象

错误做法：

```text
物料轨保存一套数据
位置轨保存一套数据
操作轨保存一套数据
然后三套数据互相同步
```

正确做法：

```text
底层事实 = 对象 + 事件 + 关系 + 时间 + 值 + 分支 + 锁点
轨道 = 对底层事实的不同过滤和排列
```

这能避免同步地狱。

### 6.5 热区、冷区与操作片段

冷区和热区首先描述 DAW 中线段与过程的呈现状态，不是工作区图层，也不是让对象从空间画布中消失的过滤器。

- 热区汇集被搬出来操作、正在参与变化、正在编辑或被选中的片段。这里的线段可以汇聚、转化、产生新对象或形成分叉。
- 冷区显示当前没有参与主要操作、但在指定时段仍存在的对象、位置关系和过程。它用于回答“这个时段还有什么”，线段可以更平静地横向流过，不自动折叠成操作。

工作区可以反映当前选中、参与和有效状态，但热区/冷区本身不接管空间可见性。对象从热区撤下，只表示其当前操作或变化阶段结束，不表示对象消失、删除或被移出事实底座。

DAW 有一条当前时刻指针（playhead）。它是用户注意力、观察和编辑的锚点：新片段默认落在指针处，双击轨道可把指针移到该处，空格（或播放/暂停控制）可沿时间查看。它与剪辑软件语义一致；"当前时刻"是用户的工作位置，不是强制约束。

CakeCAD 不应把所有操作坍缩为瞬时点。动作默认拥有持续时间；没有明确输入时可以使用短默认时长（例如 5 秒）作为可编辑片段，而不是只有 timestamp。用户应能拖动片段整体、拖动首尾边界像关键帧一样改变开始和结束，并在结束位置明确表达开放、未知或已结束。

一个片段结束或不再需要主动操作时，可以从热区撤下，只作为历史、位置或存在事实继续显示。这不等于时间事实被删除。

用户可以在轨道空白处或对象上下文菜单中新建对象，并使用类似剪辑软件的拖动、移动、裁切、延长、对齐和多选操作编辑时间片段。具体快捷键和视觉布局后续另行验证。

节点图与 DAW 不互相同步两份内容：二者是同一事实的不同投影。节点图更强调依赖和连接，DAW 更强调时间、持续区间和当前操作。

## 7. 容器、组合体与“什么时候成为新对象”

容器是独立对象。物料进入容器，不自动变成“饼干碎碗”这种新物件。

例如：

- 碗 D 是对象；
- 饼干碎 A 是对象；
- 糖 B 是对象；
- `A located_in D` 和 `B located_in D` 是关系。

只有当用户明确需要把某个内容视为一个可独立流转、引用、命名或分析的中间体时，才固化为新对象。

例如用户说“这就是曲奇面团”，系统才创建或确认一个可引用对象“曲奇面团”。

## 8. 不守恒、损耗与人工覆盖

CakeCAD 必须允许暂时不守恒，但不应把所有差异都混称为“损耗”或“余量”。

至少要区分：

- 未分配质量：输入 1000g，下游只分配 920g，剩余 80g 有依据但尚未处置；
- 已知损耗：切边、蒸发、残留等用户确认或模型确认的损耗；
- 未知损耗：总量对不上但原因未知；
- 测量残差：实测与理论差异；
- 计划余量：有意保留的备用量；
- 人工覆盖差异：用户直接把某个派生值改成另一个值造成的差额。

重要纠正：上游有依据的剩余量不是“不守恒余量”。真正的不守恒通常发生在用户直接覆盖某个派生或输入数值，而不立即补全其来源时。

## 9. 调和 Reconcile

CakeCAD 允许用户暂停约束、自由编辑，然后恢复一致。

产品术语建议使用：

- 暂停约束；
- 恢复一致；
- 调和；
- Reconcile。

不要默认叫“退火”，以免误导为一定使用模拟退火算法。

恢复一致时，系统不应静默执行。一个合理流程是：

1. 计算影响范围；
2. 找到断点；
3. 找到锁点；
4. 找到可调整变量；
5. 找到可接受差异；
6. 生成候选方案；
7. 显示将修改什么；
8. 用户确认；
9. 写入新事件或新分支。

## 10. 跨时间、跨项目的组分复用

CakeCAD 必须区分两种本质不同的“引入”。

### 10.1 物料流转

物料流转表示现实或计划中的某批物料从一个位置、对象或过程进入另一个位置、对象或过程。

例如：

- 从当前这锅草莓酱中取 200g 加入蛋糕；
- 从碗中倒出一部分面粉；
- 将裱花袋中的奶油挤入泡芙。

这种引入涉及数量、剩余量、来源、损耗、时间和守恒。

### 10.2 组分/配方实例化

组分复用表示把另一个对象、过程单元或项目中的配方与组成拿来，在当前位置创建一个新的实例。它不是从原批次中倒出物料，也不消耗原对象的数量。

例如：

- 草莓酱作为一个独立项目先被设计和记录；
- 制作蛋糕主体时，引用该草莓酱的配方组分；
- 当前蛋糕项目原地创建一份新的草莓酱实例；
- 新实例继承配方、组成、必要过程与来源说明，但拥有自己的批次、数量、时间和执行事实。

因此，用户可以在后面的设计中发现前面需要某个复杂中间体，然后直接引用其配方并创建实例。设计信息可以跨越时间顺序和不同项目复用；现实物料仍遵守各自批次的时间与数量。

正式原则：

> 配方和组成可以跨时间、跨项目复用；物料批次不能因此被伪装成跨时间流动。

### 10.3 引用与复制需要区分

跨项目复用至少存在两种候选语义，当前不锁死具体实现：

- 快照复制：复制引用时的配方和组成，之后彼此独立；
- 受控引用：保留对来源定义的引用，来源变化时只提示影响，由用户决定是否更新。

无论采用哪种方式，都必须避免循环引用。系统不能允许 A 的定义依赖 B、B 的定义又依赖 A，最终无法确定任何一方的组成。

### 10.4 分支与独立工作对象不是一回事

Branch 表示同一个项目历史中的变体。独立 Project、独立文件或独立过程单元则可以拥有自己的对象、笔记、时间、分支和分析。

不同分析算例、配方实验或中间体不一定都要成为主项目的分支。它们可以是：

- 当前项目中的普通分支；
- 当前项目内的独立过程单元；
- 独立工作文件；
- 被其他项目引用或复制的配方定义。

### 10.5 项目包、内嵌单元与外部引用

CakeCAD 默认采用“项目包中可以包含多个过程单元”的概念模型，不强迫用户预先区分机械 CAD 式的零件和装配体。

一个过程单元可以拥有自己的 Markdown、对象、时间范围、分支和分析，并且可以：

- 内嵌在当前项目中，类似虚拟零件；
- 独立保存并单独打开；
- 从内嵌状态提取为独立文件；
- 作为配方定义被其他项目实例化。

草莓酱、塔皮、酱汁、酸种等复杂中间体都可以成为过程单元。主项目引用的是其配方/过程定义，并在当前项目中创建具有独立数量、时间和批次的实例。

首版外部复用的默认语义是“锁定版本的受控引用”：

- 引用明确指向来源定义的某个版本；
- 来源后续变化不自动改写使用方；
- 系统可以提示有新版本；
- 用户查看差异后手动选择是否更新；
- 更新生成可追踪事件，不能静默发生。

用户也可以显式转换为完全独立的快照副本，之后不再跟踪来源。

外部定义依赖必须保持无环。一个定义不能直接或间接依赖自己。如果某次引用会形成循环，系统应拒绝建立实时引用，但可以允许用户导入一个断开来源的快照副本。

内嵌与外部是存储和复用方式，不决定语义地位。过程单元移动到独立文件后，其稳定身份、来源和历史关联不应无故丢失。

## 11. 分支原则

分支不要求用户提前分类。用户可以随时分支，之后再命名、比较、标记用途。

分支继承规则应遵守：

- 分叉前共享祖先；
- 分叉后未修改字段可以继承；
- 分支主动修改形成 override；
- 冲突字段不自动覆盖；
- 触碰实测或执行锁点时停止传播；
- 派生值可重算；
- 分析结果按依赖失效。

破坏性分析应进入分支。所谓破坏性包括：

- 分析需要强行修复主线不守恒；
- 分析会改变主线事实；
- 分析需要假设与主线不同的条件；
- 分析本身产生一个新情景。

## 12. CAD / PLM / CAE / CAM 的关系

CakeCAD 不应强迫 CAD、PLM、CAE、CAM 共享同一个“完整对象”。

同一个东西：

- 在 CAD 里是形状、尺寸、位置、装配关系；
- 在 PLM 里是身份、来源、批次、版本、历史；
- 在 CAE 里是材料、边界条件、初始条件、模型参数；
- 在 CAM 里是可制造路径、设备动作、工序约束。

它们应从同一个时间化研发事实底座中按需切片、转换、解释。

不对齐不是失败，而是现实本来如此。

## 13. 懒仿真与分析

CakeCAD 的仿真不是全局持续运行的物理世界。它是按问题局部调用的分析能力。

基本原则：

- 不提就不仿真；
- 无数据可以沉默；
- 有实测数据则局部利用；
- 有论文或经验式则以模型胶囊形式接入；
- 有单点数据只做保守有限泛化；
- 多点数据才考虑拟合或机器学习；
- 模型必须说明来源、适用范围和不确定性；
- 分析只在所需局部闭合。

### 13.1 分析不等于网格

食品研发中的很多问题不适合一上来做网格、FEM、CFD 或全耦合 PDE。CakeCAD 更倾向：

- 从空间形态提取形态学参数；
- 抽成 1D/2D 简化模型；
- 接数据管道、经验式、无量纲量或实测拟合；
- 必要时导出给专业工具，而不是自己变成专业工具。

### 13.2 分析可以有变量与表达式

用户可以在当前现场中声明变量、绑定对象属性、输入表达式、描点拟合。

例如柠檬精油：

- 时间轴拉到 30 分钟；
- 直接赋值 5g 柠檬精油；
- 绑定来源为柠檬皮；
- 过程选当前蒸馏装置组；
- 产率模型可以是线性、表达式或后续拟合。

这种做法体现：结果可以先存在，解释后补，模型最后选。

### 13.3 分析的五种使用方式

分析按它在用户工作中的位置分为五种使用方式：

1. 快速计算器：独立回答一个局部问题，可以不绑定项目事实；结果默认只是临时参考。
2. 先验建议：在用户执行操作前读取当前条件，给出可行范围、风险或建议，不自动修改设计。
3. 过程指导：在操作进行中结合时间、观测和测量给出观察窗口、提醒或停止条件。例如“继续加蛋，直到颜色和流动性达到目标区间”。
4. 后验检查：对已经记录或执行的过程做验证、偏差分析和失败复盘；不得反向重写实测事实。
5. 反事实/破坏性算例：假设提前出锅、改变配方、强制守恒或改变边界条件；如果要把候选状态实例化为可编辑对象，必须进入独立分析情景或分支。

这五类描述“用户为什么运行分析”。以下属性与类别正交，必须另外记录：

- 静态或随时间演化；
- 确定性、区间、概率或离散结局；
- 只读或产生候选状态；
- 使用先验、实测、文献、拟合或外部求解器；
- 是否需要几何以及所需几何保真度。

分析结果始终是派生解释，不自动成为事实。用户采纳建议时，系统通过新的命令、事件、测量或分支写入事实；校准产生新的模型版本，也不能改写旧算例当时使用的模型。

## 14. 节点图与数据管道的定位

节点图是 DAW 时间轨道的另一种结构表达，也是当前 DAW 方案的概念前身之一：节点图强调对象、依赖和连接，DAW 强调这些事实何时存在、持续多久以及当前发生什么。二者读取并编辑同一事实底座，不是两套需要同步的数据。

CakeCAD 不刻意回避图结构。节点图可以在依赖、数据管道、分析接线或调试比时间轨更清楚时出现，但不作为所有用户操作的必经入口。

但正式原则是：

- 表层交互直接操纵优先；
- 用户不应被迫先进入节点图才能做事；
- 节点图不继承 chat2 的过时数据模型；
- 节点、端口、连线、类型检查等细节暂不定死；
- 如果使用节点框架，优先复用成熟框架，不从零自研；
- 图结构服务于当前事实底座，而不是替代产品本体。

空间语义可以逐步形成数据管道：

```text
摆放 → 声明关系 → 可选接线 → 赋值 → 分析时编译
```

数据管道不仿真时可以休眠。

## 15. 近期技术路线（原型基线已定，长期桌面壳未定）

CakeCAD 是在用户电脑上运行的本地用户端，不是 SaaS。首个源码原型采用本地后端 + localhost 前端：Node.js/TypeScript 核心只监听 `127.0.0.1`，React 前端通过本地 HTTP API 使用它；不要求登录、远程服务器或云端数据库。

当前结构：

```text
用户电脑
├── 本地 Node.js/TypeScript 应用核心
│   ├── 项目文件读写
│   ├── 领域逻辑
│   ├── 状态/事实底座
│   ├── 分支与历史
│   ├── 调和与影响预览
│   ├── 分析调度
│   └── 可选 AI 调用
│
└── 浏览器前端
    ├── React UI
    ├── 3D 视图
    ├── 时间轨道
    ├── Inspector
    └── 交互状态
```

浏览器负责 UI、二维/三维视图、交互和临时视图状态。核心数据、业务逻辑、物料账本、版本和分析调度应在本地应用核心中。

这不等于 SaaS。浏览器只是当前源码原型的用户界面载体；所有首要能力在本机运行，项目数据保存在本地，可选云端 AI 不得成为基本编辑和读取的前提。

原型技术基线见 `docs/adrs/0001-localhost-prototype-runtime.md`：Node.js 24 LTS、pnpm、TypeScript、React/Vite、Fastify、Zod、Vitest 与 Playwright。首个纵切以 HTML/SVG 实现二维代理工作区和时间轨。

当前不创建 Electron/Tauri 工程。后续封装时可以由 Electron 托管 Node.js 核心，或将 Node.js 核心封装为 Tauri sidecar；桌面壳选择需在原型验证后另写 ADR。

## 16. 稀疏形态与按需几何

CakeCAD 保留空间工作区和具体几何，但不建设“所有对象、所有时刻都拥有高保真 3D 资产”的世界。

正式原则：

> 形态是稀疏、可升级的表达，不是对象存在的前提，也不是对象真实性的证明。

对象可以先有名字、身份、位置、历史和关系，只用一个代理形体或便签表示；也可以先拥有一个精细形状，再向上游补充物料、工艺和来源。

因此以下两条建模方向是对称的：

- 从原料和过程向下游生长，最后获得具体形态；
- 从月饼、蛋糕切面等具体形态出发，向上游补齐组成和过程。

### 16.1 默认使用语义代理物

大多数中间状态不值得制作专用资产。例如碗中的面糊、厨师机、烤箱、暂存物料和蒸馏瓶中的液体，都可以由简单原语、符号、标签或便签代理。

代理物主要回答：

- 这里有什么；
- 它在哪里；
- 它与谁相邻、包含、接触或连接；
- 当前对象叫什么；
- 用户和系统目前知道它的哪些事实。

代理物不应假装自己准确表达了真实外形、材质或物理状态。

空间状态仍不自动等同于业务事实：把刀放在派旁边不代表切割，把冷凝器靠近蒸馏头不代表已连接，把牛排放进水浴容器不代表已经开始 sous-vide，两个模型穿插也不代表已经混合。空间关系进入物料、过程或分析事实，仍需要用户确认、模板、声明或分析编译。

### 16.2 几何保真度按对象、按时刻独立升级

几何不是整个项目统一选择的精度。任意对象在任意受关注时刻都可以单独加深表示，例如：

```text
便签/代理物
→ 示意原语
→ 参数化形态
→ 外部导入或专业工具制作的精细模型
```

以上只是保真度方向，不预先锁死固定等级、名称或实现方式。

典型需要具体形态的对象包括：

- 定制月饼的花纹与切面；
- 蛋糕分层剖面；
- 编织派皮；
- 拉糖或巧克力造型；
- 需要提取形态学参数的局部分析对象。

具体形态通常集中在成品或关键中间态，但不限定只能发生在流程末端。

### 16.3 几何升级不改变语义地位

精细模型和简单代理物在对象身份、历史、物料关系、测量、分支和分析资格上平等。

- 精细模型不会因为漂亮而自动获得可信物性；
- dummy 不会因为简陋而失去物料和 PLM 能力；
- 几何变化不会自动重写对象传记和物料事实；
- 分析需要的几何信息仍要明确提取、声明或测量。

可以概括为：

> 形态是表达，不是承诺。

### 16.4 专业形态优先导入

CakeCAD 不需要为了少量高保真对象重造完整建模器。专业形态可以在 Rhino、Blender 或其他专业工具中制作，再导入 CakeCAD，与身份、来源、时间和过程连接。

是否提供参数化模板、极简建模工具以及支持哪些格式，后续根据首个纵切决定。

### 16.5 对象传记是派生视图

代理物旁可以显示对象传记：一段对其身份、关键历史、来源、状态和异常的浓缩描述。

例如：

> 以特定角度贴合派盘、沿边修整并在底部叉孔的塔皮。

传记必须是带来源的派生视图，而不是另一份手工维护的事实。它可以由确定性规则或 Agent 从以下来源生成：

- 已确认事件；
- 有效关系；
- 用户命名；
- 测量；
- 原始 Note 与锚点；
- 当前分支和时间位置。

传记中的每个重要陈述应可回查来源。用户可以追加批注或修改原始事实，但不能通过直接篡改派生摘要制造与事实底座不一致的第二份真相。

### 16.6 视觉语言：深色实验室 × 纸质便签

美术方向已定（详见 `docs/specs/visual-style.md`，风格来源 chat6）：外壳采用深色工程实验室风——近黑背景、琥珀色克制强调、等宽仪表字体、细边框；对象代理物保持纸质便签/侦探板质感。两者融合：外壳是仪器，对象是证物。

chat6 的六模式导航、3D 视口永久居中和文档双向自动生成不采用；便签的具体排版、图标和动效仍待原型迭代。

视觉表现的核心纪律是：

> 信念感来自同一事实在标签、时间轴、来源和对象库中的一致性，而不是资产精细度。

### 16.7 视觉颜色与分析呈现

默认颜色主要用于身份区分和对象角色提示，而不是宣称真实材质或分析结论。

- 对象名称应以明确文字标题为主，例如便签上直接写“奶油”“刀”“厨师机”。
- 食材、工具、设备、Stub 等大类可以使用横杠、边框、图标或基础色作为辅助区分。
- 同类对象不应仅靠颜色辨认，避免颜色数量爆炸和无障碍问题。
- 用户可以自由修改对象或便签颜色；该颜色默认属于显示样式，不自动改变材料、配方和物性。

分析推导外观不要求拥有网格，也不等于写实 3D 预览。分析可以按现有表示能力选择：

- 在代理物上叠加色带、徽标、边框或透明覆盖；
- 在便签上显示结果卡、等级、区间或小图表；
- 在时间轨上显示曲线、窗口和风险区段；
- 只有已有适用几何时，才在剖面或表面显示空间分布。

任何模型推导的颜色或外观都必须有独立图例、来源和开关，不能与用户自定义颜色混为一谈。

## 17. UX 工作面与信息分区

CakeCAD 大体需要容纳以下工作面：

- 工作区/空间现场；
- 命令或直接操作入口；
- 时间轨道（借鉴 DAW，但不是照搬 DAW）；
- Markdown 研发底稿；
- 对象、属性、来源、冲突与分析信息；
- 可能存在的节点图、数据管道或其他深层视图。

这些工作面的存在大体明确。布局骨架已按 chat6 参考图拍板：顶栏 → 视口条 → 左侧工具栏 + 中央工作区 + 右侧栏（Markdown/Inspector/CMD 终端）→ 底部 DAW（走带/时间码/轨道头/片段/playhead）→ 状态栏，详见 `docs/specs/visual-style.md` 第 6 节。面板尺寸的精细比例与折叠行为仍待原型迭代。

面板尺寸、折叠行为和密度仍按任务流程与原型测试迭代，清单本身也允许增补工作面；但骨架结构不再每张草图推翻重来。

重要交互原语：

- 在时间线上建立对象存在区间；
- 从多个来源建立绑定；
- 将空间关系提升为物料关系；
- 容器内容默认折叠；
- 未知时间以虚线或模糊区间表达；
- 修改时提供影响预览；
- 一键创建情景分支；
- 自然语言事件可在 3D 空间与时间线上双重锚定。

## 18. 首个纵切 Demo 候选：曲奇

本节已展开为下游规格 `docs/specs/cookie-first-slice.md`。该规格冻结首个验证版本的范围，但不把临时 UI 和实现选择提升为长期产品约束。

曲奇流程比完整 CakeCAD 小，但能暴露关键设计。

候选故事：

1. 用户先写一段不完整 Markdown。
2. 在空间中摆出碗、原料、厨师机和烤盘。
3. 用空间操作把原料放入碗。
4. 启动一段持续混合过程。
5. 在搅拌中途加入黄油、蛋和巧克力豆。
6. 用户把当前混合物命名为“曲奇面团”。
7. 将面团分成若干份，质量可以未知或近似。
8. 在烤盘上自由摆放。
9. 将烤盘放入烤箱。
10. 烘烤时间只写成“到边缘上色、中心偏软”。
11. 用户点击快速估算。
12. 系统提示观察窗口，而不是强行给结论。
13. 用户补入实际烘烤时间和出炉质量。
14. 系统做后验比较。
15. 用户从混合步骤创建“黄油软化版”分支。
16. 两个分支共享上游，局部变化，结果可比较。

这条流程体现：自然语言自由、空间操作自由、对象有时间区间、容器独立、物料关系可后绑定、时间可以未知、状态可以用户命名、质量可以暂时不守恒、分析按需发生、后验数据可回填、分支不污染主线。

## 20. 文档治理规则

本文件是正式总文档，但它不是第 0 级主体。文档体系的完整层级：

```text
L0  原始材料（coffeehour、对话、原型体验发现）
L1  docs/LEDGER.md 研发台账——每个原始点的归档与处置记录
L2  本文件——台账蒸馏出的现行结论
L3  specs / ADR——下游展开
L4  代码
```

原始点一律先进台账，处置（吸收/转化/砍/挂起）落实后才改写本文件；本文件只呈现当前结论，研发过程的痕迹由台账保存。

下游文档可以包括：

- ADR：记录重大设计决策；
- Feature Spec：记录单个可实现功能；
- TRD：记录某个技术方案；
- UX Spec：记录详细交互；
- Research Note：记录调研，不自动转正。

但下游文档必须遵守：

- 不得重新定义本文件中的核心概念；
- 发现冲突时先修改本文件或写 ADR；
- 不得把 coffeehour 原文直接当规范；
- 不得把 chat2 的过时技术细节重新引入为约束；
- 不得为了显得完整而平行生成一堆互相争权的文档。
