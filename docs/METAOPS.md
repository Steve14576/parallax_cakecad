# CakeCAD 元操作研究（METAOPS）

> 层级：L1 研究文档 · 状态：研究中（结论成熟后回写 `MASTER_SPEC.md` B.4 / C.13）  
> 动机：现有命令清单（B.4.3，16 个）是一拍脑袋的平面列表；菜单（B.4.5）有注册表没有的动词；内核事件（C.13，17 种）与命令从未对齐。必然存在"大操作是小操作的组合"，也必然撞车、不正交。  
> 方法纪律：**不预设正交性为目标。** 判断标准只有两个——事实（它到底往事实底座写了什么）与实践（工作流频率、心智模型、承诺级别）。重合不等于错误，但重合必须被看见、被命名、被裁决。
>
> 阶段纪律：项目仍在 PRD/TRD 阶段，需求本身还在变。本文件的 F 原语、内核事件名、plane 字段等全部是**概念层记账工具**（用来检查和裁决，不是用来实现），禁止把任何条目当作函数签名、类名或数据结构定稿。

---

## 1. 三个层面

操作体系不是一张平面表，而是三层：

```text
L-cmd    用户命令     人看到的动词：倒入、混合、分件……（B.4.3，16 个）
L-kernel 内核事件     事件日志里的类型：transfer、combine、process_start……（C.13，17 种）
L-fx     效果原语     对事实底座的最小突变：对象出生、关系开闭、标签挂载……（本文件首次定义）
```

约束方向：

- **效果原语必须可数、可撤销**——撤销系统（L017）最终建立在它上面；
- **内核事件尽量小且互斥**——同一类事实变化只应有一个事件类型能写它，否则事件日志失去唯一真相的地位；
- **用户命令允许重叠、允许是宏**——命令为工作流服务，不为代数 purity 服务；但同一内核写入不得因入口不同而不同（一致性底线）。

## 2. 效果原语清单（L-fx）

对事实底座的所有可能突变，穷举如下。任何命令、任何内核事件，最终都只能由这些原语组合而成：

| 编号 | 原语 | 说明 |
|---|---|---|
| F1 | 对象出生 | 创建新身份（含过程中的暂定产物） |
| F2 | 对象退役 | 结束存在区间（消耗/废弃；不是删除，历史保留） |
| F3 | 关系开区间 | located_in / derived_from / conforms_to 等生效 |
| F4 | 关系闭区间 | 上述关系失效（记录终点） |
| F5 | 标签挂载/摘除 | "正在消失于 P""正在被创建于 P"等稀疏标签 |
| F6 | 值写入 | ValueCell：量、参数、状态字段 |
| F7 | 锁点产生 | 实测/手动等 Lock，切断自动传播 |
| F8 | 量分配 | 质量/数量在对象间记账（转移、拆分、损耗登记） |
| F9 | 时间区间开 | 过程区间左端 |
| F10 | 时间区间闭 | 过程区间右端 |
| F11 | 名称写入 | 命名/改名 |
| F12 | 观察/注释记录 | observe、锚点、无承诺信息 |
| F13 | 绑定/解绑 | 来源、配方、变量绑定的建立与解除 |
| F14 | Recipe 结构变更 | 版本分叉、diff/merge（**不在 Run 平面**） |
| F15 | 注册表写入 | MethodDef、命令、模型胶囊登记 |
| F16 | 分析实体创建 | Question / AnalysisCase / Result |
| F17 | 文件导出 | exports/ 写文件 |
| F0 | 零写入 | 纯视图操作 |

## 3. 内核事件 → 效果原语

C.13 的 17 种内核事件逐个拆成原语，验证内核是否互斥：

| 内核事件 | 原语组合 | 互斥性检查 |
|---|---|---|
| create | F1 | 干净 |
| transfer | F8 + F3/F4（位置关系迁移）+ F6（量记录） | 干净 |
| combine | F9 + n×transfer + F5 + F1（暂定产物） | ⚠ 内含 transfer，见 §5-C3 |
| separate | F1×N + F13（derived_from）+ F8（分配） | 干净 |
| place | F3/F4（仅 located_in，不动账） | 与 transfer 的边界见 §5-C4 |
| process_start | F9 | 与 combine 撞，见 §5-C3 |
| process_end | F10 + F5 摘除 + F1/F2 状态迁移 | 干净 |
| pause / resume | F5（过程状态标签） | 干净，但尚无命令 |
| intervene | F12 + F6（过程内记录/参数变更） | 干净，但尚无命令 |
| abort | F10 + F2/F5（中止语义迁移） | 干净，但尚无命令 |
| measure | F6 + F7 | 干净 |
| observe | F12 | 干净 |
| annotate | F12（带锚点） | ⚠ 与 observe 边界模糊，见 §5-C6 |
| name | F11 | 干净 |
| bind / unbind | F13 | 干净，但尚无命令 |

**结论 A**：内核大体互斥，真正的问题集中在三处：combine 与 process_start 的包含关系、place 与 transfer 的边界、observe 与 annotate 的重合。

## 4. 用户命令 → 内核事件分解

B.4.3 全部 16 个命令逐个分解，并标注所在平面：

| 命令 | 内核分解 | 平面 |
|---|---|---|
| new 新建对象 | create（+place，若拖入时指定位置） | Run |
| name 命名 | name | Run |
| place 放入 | place | Run（declared） |
| pour 倒入 | transfer + place | Run（committed） |
| takeout 取出 | transfer（+create，若取出物需独立身份） | Run（committed） |
| mix 混合 | combine（= process_start + n×transfer + 双向缓冲标签） | Run（committed） |
| split 分件 | separate | Run（committed） |
| start 开始操作 | process_start | Run（committed） |
| end 结束操作 | process_end | Run |
| measure 记录测量 | measure | Run（measured） |
| record 回填实测 | measure（目标=过程/Run） | Run（measured） |
| ask 提问 | Question → AnalysisCase（F16） | Analysis |
| fork 新建版本 | Recipe 分叉（F14） | Recipe |
| lanes 召唤泳道 | 无（F0） | 视图 |
| export 导出手册 | 无事实写入（F17） | 文件 |
| defmethod 新建方法 | MethodDef 登记（F15） | 注册表 |

**结论 B（重要）**：16 个命令横跨五个平面（Run / Recipe / 注册表 / Analysis / 视图+文件）。命令注册表必须为每个命令声明 `plane` 字段，否则"撤销"这个词对不同命令意味着完全不同的东西——撤销 pour 是回退事件，撤销 fork 是删除未引用版本，撤销 lanes 根本没有意义。这是旧命令清单完全没处理的维度。

**结论 C**：mix 是唯一的真复合命令：一次 mix = 1 个 process_start + n 个 transfer + 标签挂载 + 暂定产物出生。中途加黄油就是区间内再发一条独立 transfer——所以"打面中途加料"不需要新命令，pour 天然支持（目标=进行中的过程）。

## 5. 撞车矩阵与逐对裁决

以下每对都写入相同或高度重叠的内核事件。逐对给出：事实差异（写的东西差在哪）、实践差异（用起来差在哪）、裁决草案。

### C1：pour 倒入 ↔ takeout 取出

- **事实**：同为 transfer。方向相反；takeout 可能多一个 create（取出的那一份要不要变成独立对象）。
- **实践**：倒入是生产主流（目标=容器/过程）；取出是熵减/纠错/取样主流（目标=台面/新 Pile/废弃）。
- **草案**：内核合并为单一 transfer(from, to, 量)；命令层保留两个动词——提示语、默认目标、角色过滤器都不同，合并成一个"转移"动词会逼用户每次额外指定方向。**允许不正交，理由=心智模型不同。**

### C2：record 回填实测 ↔ measure 记录测量

- **事实**：完全同内核（measure），仅宾语类型不同（对象 vs 过程/Run）。
- **实践**：用户在曲奇流程里会在对象上测（面团 80g）也会在过程上回填（烘烤实际 13min）。
- **草案**：**合并为 measure**，签名目标槽位放宽为 object|process|run。少一个动词，无信息损失。待用户确认。

### C3：mix 混合 ↔ start 开始操作

- **事实**：mix = start(type=combine) + n×transfer + 双向缓冲。start 是 mix 的真子集。
- **实践**：混合是最高频过程且入口物料必须在启动瞬间动账，值得一个一键动词；通用 start（烘烤、冷藏、静置）不需要立即动账。
- **草案**：**保留 mix 作为 start 的便利封装**，但规格必须写明：mix 不产生任何 start 表达不了的事实，二者共享同一 process_start 内核。combine 不再作为独立内核事件，降级为 process_start 的 type 参数 + 自动伴随 transfer——这同时解决 §3 里 combine 与 process_start 的互斥性问题。**这是"大操作=小操作组合"的第一个正式实例。**

### C4：place 放入 ↔ pour 倒入

- **事实**：place 只写 located_in（declared，不动账）；pour 写 transfer+located_in+量（committed，动账）。pour ⊃ place 的空间效果。
- **实践**："把碗放进烤箱"与"把面粉倒进碗"在承诺级别上完全不同——前者是摆位，后者是物料账本变更。若不区分，用户每次摆位都被迫声明量，或每次倒料都逃账。
- **草案**：**保留两个动词，边界用承诺级别写死**：place=declared/不动账；pour=committed/动账。角色过滤器辅助：pour 的主语必须是 material。**允许语义重叠，理由=承诺级别不同；这正是"操作自由，仿真诚实"在命令层的体现。**

### C5：takeout 取出一部分 ↔ split 分件

- **事实**：从一团面取 50g，和把面团分成 6 份，都是量的切分；区别在 separate 创建 N 个带来源关系的子对象（身份），而 takeout 的量可以没有身份（倒进垃圾桶不需要传记）。
- **实践**：取出的东西如果需要被后续追踪（取样送检、留种），它就是对象；如果不需要（丢弃、试吃），它只是账本数字。
- **草案**：边界规则=**身份需求**。takeout 默认不创建对象，选项 `--as-object` 升级为 separate 的 1:1 特例。split 保持 N 路等分/指定分配。**这条规则同时回答"取出来的算不算新对象"这个旧坑。**

### C6：observe 观察 ↔ annotate 注释

- **事实**：同为 F12，区别只在是否带对象锚点。
- **草案**：**内核合并为 observe（可带锚点列表）**，annotate 降级为别名。"插入书签到 MD"命令写的就是 observe+锚点。

### C7：new 新建 ↔ 过程产物出生

- **事实**：两条对象出生通道——用户显式 create，与 process_end/combine 内部的产物 create。
- **实践**：前者是用户主动引入，后者是过程推导（临时名可后改）。
- **草案**：内核统一为 create（source 字段区分 manual / process_output）。无需新命令，但 Inspector 传记必须能区分两种出生。

### C8：菜单孤儿（B.4.5 有、B.4.3 没有的动词）

| 菜单动词 | 对应内核 | 处置草案 |
|---|---|---|
| 暂停 / 介入 / 中止 | pause / intervene / abort | **补正式命令**（过程区右键）。3D 打印换色、中途翻面团都需要 |
| 恢复（resume） | resume | 内核有但菜单漏了，一并补 |
| 绑定来源 | bind / unbind | **补正式命令**（多选区）。5g 精油后补来源靠它 |
| 装配 | combine 子类型 assemble | **暂缓**，作为 MethodDef 或 start(type=assemble) 处理，不单立动词 |
| 清空 | transfer（全部→废弃）+ F4 | 草案：takeout --全部 --to 废弃 的别名，不单立 |
| 标记已清洗 | observe + 状态标签（F5/F6） | 草案：name/observe 类轻命令，可补 `mark` 通用标记命令 |
| 设定参数 | F6（设备 ValueCell） | 草案：补 `set` 命令（object × 参数 × 值） |
| 查看档案 / 插入书签 / 撤下带入热区 | F0 / F12 / F0 | 视图与导航动作，**不进命令注册表**，归为 UI 动作层 |
| 移动 move | 画布坐标 | **关键裁决**：坐标是纯视图状态还是事实？草案=视图状态不进事件日志（除非用户把位置提升为 Region/关系），move 不做命令，拖拽与 CMD 坐标输入直接写视图状态 |

### C9：undo / redo

- 每个命令都声明了"撤销"，但没有 undo 命令本身。
- **事实问题**：Run 是 append-only，撤销 pour 不能删事件，只能发**补偿事件**（compensating event）或在 Recipe 层做真删除。两个平面的撤销语义不同。
- **草案**：undo/redo 进注册表，plane=meta；Run 平面撤销=追加补偿事件（账本风格），Recipe 平面撤销=真回退（未执行的设计无账本义务）。**这同时是 L017（撤销/历史树）的第一个正式结论。**

## 6. 组合律：大操作如何由小操作合成

从曲奇与 chat 资料里的真实流程归纳：

```text
打面      = mix + 0..n×pour(中途) + end
烘烤      = start(type=bake, 设备) + … + end + record(实测)
分团整形  = split(N) + 0..n×place
取样送检  = takeout(--as-object) + name + place(送检区)
清洗归位  = takeout(残余) + mark(已清洗) + place(归位)
腌制/冷藏 = start(type=marinate/chill) + end（无动账，纯时间区间）
```

**推论 1**：用户级"大动词"（烘烤、腌制、水浴……）**不应进命令注册表**——它们是 start 的 type 参数，或用户自定义 MethodDef 的模板。注册表保持小（约 20 个），方法库无限生长。这把"阿姆斯特朗烤箱"式自定义和通用命令的边界正式画出来了。

**推论 2**：复合的唯一合法机制是**命令发出一串内核事件**，不存在命令调命令。这保证 CMD 内联、右键、工具栏三个入口行为一致，也保证撤销可以按事件粒度回退。

## 7. 非正交性政策（草案）

1. 效果原语层：可数、可撤销，变化不重叠。
2. 内核事件层：互斥优先；发现的非互斥（combine）降级为参数化。
3. 用户命令层：**允许重叠**，但每处重叠必须在本文件登记（§5），且写明实践理由；无理由的重合视为事故。
4. 同一内核写入不得因入口（右键/工具栏/CMD）不同而不同。
5. 菜单与注册表必须一一对应：菜单里出现的每个动词要么在注册表、要么明确属于 UI 动作层（F0/F12 类）。

## 10. 不可穷举操作：能力声明层（火鸡情景研究）

来源：用户提出的火鸡情景（L046）——右键火鸡，新建或复用一个动作"掰下它的右侧 drumstick"；更有甚者烤到一半"打开烤箱并掰下右侧 drumstick"。同类：芒果塔派盘皮修边、火鸡塞料。这是**难以提前穷举预测的高自由度操作**的样本。

### 10.1 先验证：事实层用现有原语能否表达

"烤一半开门掰右腿"全部分解为已有内核：

```text
intervene(烘烤过程 P)        ← 开门，过程内介入事件（内核已有 pause/intervene/resume）
split(火鸡, part=右drumstick) ← separate 内核，子对象带来源关系
  （取出则再 takeout；留在烤箱则无后续）
resume(P)
```

结论：**操作层没有缺口**。真正的难点只有一个——"右侧 drumstick"这个部分从哪来？

### 10.2 命名部件目录（named parts）

草案：对象可以携带一份**部件声明**——火鸡的官方能力包声明"有四肢（左腿/右腿/左翅/右翅）""能塞入（腹腔）""能被切"。关键规则：

- 部件被操作前**只是声明的潜在分界**，不是对象，不产生账本；
- 被掰下/切下那一刻才实体化为子对象（F1 + derived_from + from_part=右腿）；
- 这是懒身份：与懒语义、懒仿真、懒几何同族的第四条懒原则候选。

### 10.3 "能从中间劈开的"是什么：能力声明（affordance）

逐条排除：

- **不是过程**——过程是已发生或正在发生的事，能力声明什么都没发生；
- **不完全是 MethodDef**——MethodDef 是"怎么测、怎么算"的用户方法（带指标）；能力声明是"能被怎么操作"；
- **不是普通标签**——它带宾语签名和后果模板，是可被调用的。

草案定义：**能力声明 = 谓词 + 宾语签名 + 默认后果模板**，挂在对象或对象类上，是注册表数据。调用它产生的动作才是过程/事件。

后果自定义（用户原话的落地）：调用时后果 = 模板默认（split + 质量分配 + 标签）或当场编辑覆盖，走 Case Preview 式确认。后果由原语组合：F1 子对象出生、F5 标签（如"烤过"）、F8 量分配。没有后果也合法——纯记录动作发生。

官方与用户同构（用户明确要求）：能力包是同一注册表里的数据，官方"带有四肢的火鸡"和用户当场加的"能从中间劈开"机制完全同一条；用户能力包可存库。这把 §6 推论 1 再推进一层：不只方法库可生长，**对象能力库也可生长**，二者都是注册表数据而非代码。

### 10.4 空间语义的承载：标签层 vs 网格层

用户提出的两条路线是**并列的本体方案**（物料与性质逻辑住在哪里）：

```text
路线 A（网格本体）：对象=无碰撞布料/海绵网格，物料逻辑住在几何里——
                    节点带 voxel 与 mass，切割时现场重算节点与边拓扑，
                    切下来的部分的性质由网格分配继承
路线 B（标签本体）：便签+自然语言声明性质；图像仅展示（贴图/有限展示建模，
                    如月饼剖面只在末端画出）；后果当场自定义；能力库预置常见物料
```

关键推论（用户点明）：**若标签是本体，几何层被彻底解放。** 塔皮"能软贴合派盘、边缘能被割掉、割下来的边有自己的质量和继承参数"这类物料与性质逻辑全部由标签+自然语言承担，3D 不必为它们付任何代价——可以用非布料的普通 3D，建死物，甚至不建，它只是个草稿。

这消解了路线 A 的成本结构：网格方案的昂贵恰恰来自"它要当本体"（切割重算、节点质量、边拓扑维护）；本体让给标签之后，这套 machinery 整个不需要存在。

#### 10.4.1 双方案全面对比

| 维度 | 标签本体 | 网格本体 |
|---|---|---|
| 表达能力 | 离散符号：事件、账本、命名部件、自然语言。表达"左边焦了 2cm 一条带"笨拙 | 连续场：空间分布（温度场、厚度、偏料）天然一等 |
| 演化自由度 | 加新性质=加标签，零成本；schema 随时生长。**需求仍在变，此项权重最高** | 每类新物理行为可能要新节点属性/求解器/拓扑操作，schema 长在数据结构里，改动昂贵 |
| 诚实性 | 账目靠声明，可以错；但"未知合法""不守恒账本"本来就是核心设计，缺口由分析层指出 | 质量守恒由几何保证，切割自动分配——账目不会撒谎；**但代价是未知不被允许**，与"未知是合法状态"直接冲突 |
| 实现成本 | 本体层零图形学；图形预算全花在展示层 | 切割重算、拓扑、3D 拾取交互、渲染、性能全部进 critical path；单人+AI 工具链风险极高 |
| 体系兼容性 | 与事件日志、append-only、懒语义/懒仿真/懒身份、双向缓冲同族——全是离散符号系统 | 连续场系统与事件日志世界观冲突：每切一刀网格状态怎么 append-only？快照版本化与 diff/merge 复杂度爆炸 |
| 同步风险 | 单一事实底座 | 双本体=两套事实系统互相同步——与已废止的"全局 DAW 双向同步"同构的陷阱，更深 |

#### 10.4.2 对网格本体价值的诚实评估

网格本体真正不可替代的场景：切割/变形过程的**物理真实模拟**（拉面延展、裱花形变、翻糖贴合）。但 CakeCAD 的定位是研发过程的记录+分析（CAD/PLM/CAE），不是物理解算器；这类问题在懒仿真原则下本就"不提问就不算"。

关键缓解：**网格活在算例里，不活在本体里。** 真需要连续场时，Analysis 算例内部可以用 FEM/网格做临时内部表示，算例输出以区间/值/标签形式回到事实底座。本体层永远不需要网格。

标签本体失去的东西（诚实列出）：连续空间分布的直接表达（用命名部件/Region 离散替代）；自动质量守恒（用账本+多种未知/损耗条目替代）；切割的物理正确性（用算例按需补）。

#### 10.4.3 用户已表态的几何层定位

用户倾向（2026-09-02，待随本体裁决一并确认）：**几何层只作草稿与演示**——可以孤立存在，或被约束于一个标签作其下游可视化，**不直接参与物料流**；理由：3D 改物料逻辑的自由度不如标签灵活。此定位与已拍板的"视图是廉价投影"同构。

#### 10.4.4 草案裁决（待拍板）

- **本体 = 标签层**（对象 + 稀疏标签 + 自然语言 + 命名部件）；
- 布料网不作为本体保留；网格只允许以算例内部临时表示存在；
- 几何层 = 草稿/演示，孤立或作为标签的下游可视化，不参与物料流。
