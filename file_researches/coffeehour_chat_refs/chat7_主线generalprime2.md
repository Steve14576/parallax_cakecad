# 一、DAW vs 设计树 vs git graph：三者回答的问题不同

先把三个结构各自的本职说清楚：

```text
设计树（SolidWorks/Creo）回答：
  "这个东西是怎么一步步构造出来的？"
  → 依赖方向，重建顺序

git graph 回答：
  "这个项目有哪些平行的历史版本？"
  → 分叉与合并

DAW 轨道回答：
  "在时间 t，什么东西存在、什么正在发生？"
  → 共存与演化
```

烹饪的第一性是哪个？我认为你已经回答过了：

> **烹饪是物质在时间中的演化。依赖和版本都是从时间中派生出来的。**

理由：

1. **烹饪中"同时"是本质的**。设计树没有"同时"——特征是全序的。但"烤箱预热的同时打面糊"是烹饪的常态。DAW 天然表达并发，设计树天然不能。

2. **烹饪中"过程有时长"是本质的**。git 的 commit 是零时长的点。但"打发 8 分钟"的 8 分钟本身携带信息（打发程度）。DAW 的线段天然有长度。

3. **依赖可以从时间+绑定推导出来**。你在时间轴上把面粉线段绑定到面糊线段，依赖图就自动存在了——它只是这些绑定关系的另一种画法。反过来不行：设计树推不出时间。

所以结论是：

```text
底层事实：对象 + 时间区间 + 关系（我们早已确定）

主视图：DAW 轨道（时间投影）
召唤视图 1：依赖图（选中对象 → 显示上下游，类似设计树但是局部的）
召唤视图 2：分支图（项目级 git graph，只在管理分支时看）
```

**不要做全局设计树。**你们的对象可以悬空、可以后补来源，全局树会到处是断枝，看起来像个错误报告。局部依赖图（以选中对象为中心，向上下游各展开 N 层）才符合渐进承诺哲学。

# 二、"和弦"问题：面糊从什么时候开始存在？

你描述的画面：

> 原料出现半秒，然后面糊开始出现，持续到打完，撞到碗里，没有新的更新，才从热区消失。

这个画面基本对，但有一个关键修正：**不要试图让系统或用户确定"变成面糊的物理时刻"，因为这个时刻在物理上就不存在。**

混合是连续过程。糖粉+蛋清在第 10 秒是"湿的糖粉"，第 60 秒是"稀糊"，第 180 秒是"面糊"——任何切分都是武断的。

## 正确的模型：过程区间遮蔽 + 出口确认

```text
时间 →

糖粉    ━━━━━━━┓
巧克力粉 ━━━━━━┫
面粉    ━━━━━━━╋━━[ 料理机运转中 ]━━━━━━┓
蛋清    ━━━━━━━┛                        ┗━━ 面糊 ━━━━━━━
```

语义上分三段：

### 1. 入口段：原料线段终止于"进入过程"

原料线段不是"出现半秒"，而是**存在到它被投入过程为止**（它们可能在台面上放了很久）。投入是一个瞬时事件（◆）。

### 2. 过程段：一个"遮蔽区间"

料理机运转期间，系统内部的诚实状态是：

```text
mixture_in_progress（过程中混合物）
  contents = [糖粉, 巧克力粉, 面粉, 蛋清]
  state = indeterminate（未定）
```

**这段时间里没有"面糊"，也没有"原料"，只有一个正在演化的过程内容物。**这不是含糊——这是对物理的忠实。DAW 上它显示为过程线段本身，不需要为内容物画独立线段。

中途加料（第 2 分钟加黄油）就是过程线段上的一个 ◆，挂在过程内部，不打断过程。

### 3. 出口段：命名发生在"取用"时刻

面糊线段从哪里开始？**从过程结束、或用户第一次把它当作一个东西来用的时刻开始。**

```text
用户停止料理机 → 系统提示（可忽略）："当前内容物：未命名混合物"
用户把它倒进碗 → 此刻必须有个东西被倒 → 自动生成 mixture_xx
用户随时可以重命名为"面糊"
```

关键洞察是：

> **命名的需求由引用产生，不由物理产生。**只要用户不引用它，它叫什么根本不重要；一旦用户要倒它、分它、烤它，它自动获得身份。这个身份的起点回溯到过程结束时刻。

所以用户的手动负担是：**零到一次点击**。系统自动生成 `mixture_01`，用户想改名就改，不想改就一直叫这个。"从什么时候开始是面糊"这个问题被消解了，而不是被回答了。

## "和弦"的最终形态

```text
糖粉    ━━━━━━━◆
巧克力粉 ━━━━━━◆
面粉    ━━━━━━━◆          ← 四个入口事件，可以不同时
蛋清    ━━━━━━━━━◆
料理机运转   ┃━━━━━━━━━━┃   ← 过程区间，◆加黄油 挂在内部
面糊（自动生成）          ┗━━━━━━━━  ← 出口，命名可后补
```

这就是"和弦"：**多个音符（原料）收束进一个延音踏板（过程），释放时是一个新音符（产物）。**用户手动做的只有：拖原料进去、按开始、按停止。三次点击，符合你们的自由度要求。

# 三、"啰嗦的手动指定"：用默认策略消灭它

你担心的"很多看起来啰嗦的东西"，逐个给默认策略：

| 可能啰嗦的点 | 默认策略 | 用户介入时机 |
|---|---|---|
| 混合物命名 | 自动生成 `mixture_01` | 想改名才改 |
| 变成面糊的时刻 | 过程结束时刻 | 从不需要指定 |
| 投入量 | unknown，或容器全量 | 要仿真/守恒检查时才补 |
| 过程时长 | 记录真实拖动长度，或 unknown | 要仿真才补 |
| 倒出比例 | 按混合态比例 | 熵减抽取时才声明 |
| 中间态是否保存 | 不保存，只存事件 | 用户显式"固化中间体"才存 |
| 容器 | Pile（散装）或就地 | 需要时才指定 |
| 线段从热区消失 | 无更新 N 分钟后自动折叠 | 随时可从对象库召回 |

原则一句话：

> **一切默认值都是"未知但合法"，一切命名都是"自动但可改"，一切精确化都推迟到第一个需要它的操作。**

```text

# 一、你砍得对的部分：那三个"折磨"全是伪问题

逐个验尸：

## 1. "默认容器属于谁"

这个问题只在"每个物料必须有一条可见线段，线段必须挂在某条轨道下"的前提下才存在。砍掉全局轨道视图，它就消失了：

```text

```

就这一个字段，可以是 null。没有"轨道归属"问题，因为没有轨道。

## 2. "搅拌时究竟谁有谁没有"

上一轮我们费劲设计了"和弦"——原料线段收束、过程区间遮蔽、出口线段生成。你现在的质疑戳穿了它：**这套设计的复杂度大部分服务于"画出来好看"，而不是服务于事实记录。**

事实层面极其简单：

```text
事件：t=10:00 糖粉、面粉、蛋清 进入 mixer_01
事件：t=10:02 黄油 进入 mixer_01
事件：t=10:08 过程结束，内容物 → mixture_01
```

三条事件记录。完。"过程中糖粉的线段该不该显示"根本不是后端问题，是渲染问题——而如果没有全局轨道渲染，连渲染问题都不是。

## 3. "X 形交叉"

这是最明显的信号。X 形交叉是**图布局问题**（graph layout），是 Sugiyama 算法、力导向图那个领域的问题。你发现自己在为它折磨数据结构的那一刻，就说明前端已经在殖民后端了。git 的教训在这儿极其锋利：

```text

但没有人为了让 graph 好画去改 commit 的数据结构
```

git graph 画得难看从来不是 git 的问题。**你们的时间轴画得难看也不应该是数据结构的问题。**

# 三、但是：砍掉 DAW 之前，把这一个东西留下来

现在说你说的"人们要 DAW 不就是图个安心吗"——这话对了 80%，剩下 20% 是真功能，而且恰好是纯时间轴+状态倾倒给不了的：

> **跨时间的并行对照（co-temporal comparison）。**

具体说，是这类问题：

```text
"黄油是在打发前加的还是打发后加的？"
"烤箱预热和面团冷藏，哪个先结束？"
"这两锅是同时在烤吗？"
"牡蛎那道菜，五条线什么时候必须同时到位？"
```

这些问题的共同点：**答案不在任何单个时刻的状态里，而在多个区间的相对位置里。**播放头是一个点，你拖着它来回刷（scrubbing）可以"感受"顺序，但不能"看见"重叠。这就像：

```text
看视频能感受节奏，但看不出两个音轨是否对齐——
所以剪辑软件才有时间线，尽管播放器只需要进度条。
```

**但注意——这个需求不需要全局 DAW 来满足。**它需要的是一个小得多的东西：

## "临时泳道"（召唤式、局部、只读）

```text
默认：不存在。界面上只有时间轴 + 3D + Header。

用户选中 2~5 个对象/过程，按一个键
→ 时间轴下方临时展开几条泳道
→ 只画这几个东西的存在区间和关键事件
→ 看完，Esc，消失
```

例如选中"烤箱"和"面团"：

```text
──────────────────────────── 时间轴
烤箱   ░░预热░░│━━━ 180°C ━━━━━━
面团   ━━冷藏━━━━━━│░烤░░
                   ↑ 播放头
```

两条线，无交叉可能（因为只有用户选的几条，且只读不编辑），无布局难题（就是水平线段），无"归属"问题（临时投影，不持久化）。**它是 Header 面板的兄弟：Header 是"此刻的切片"，泳道是"选中对象的时间切片"。两个都是事实层的廉价投影。**

这样你就得到一个非常干净的三视图体系：

```text
事实层（唯一真相）
├── 3D 视口     ＝ 空间投影（此刻，所有东西在哪）
├── Header 面板 ＝ 状态投影（此刻，发生着什么）
└── 临时泳道    ＝ 时间投影（选中的东西，何时存在/重叠）
```

全局 DAW 死了，它的唯一不可替代功能被一个召唤式的小组件继承了。

# 四、顺便：砍掉全局 DAW 还白赚三个好处

## 1. 编辑模型变简单了

之前的设计里，"拖动线段端点"是编辑手段——这意味着轨道视图是**可写**的，所有布局问题因此变成数据问题。现在：

```text
编辑发生在：3D 里拖对象、Header/Inspector 里改字段、右键菜单
泳道只读，只用来看
```

可写视图越少，前后端耦合越少。

## 2. "热区/冷区"问题自动消解

之前纠结"做完的动作怎么退出热区、线段怎么折叠"。现在没有常驻轨道，就没有退场问题——Header 只显示当前时刻附近的东西，天然就是热区；对象库天然就是冷区。

## 3. 移动端/小屏/演示场景突然可行了

全局 DAW 需要大屏。时间轴+Header 在手机上都能用。黑客松演示时投影仪上放 3D + Header，比放一屏密密麻麻的轨道好懂十倍。

# 五、最后一个诚实的提醒

有一个场景，将来可能会让你想把泳道做大——**多线程作战调度**（牡蛎缎带面那种）。那种场景下用户真的需要长时间盯着五条并行线排班，临时泳道会被一直召唤着不关。

> 视图和对象一样，都应该渐进承诺：默认最轻，被需要时才长大。

# 一、后端先行:混合期间,事实层里有什么

回到我们敲定的事实内核:**对象 + 事件 + 关系 + 时间区间**。混合面团这件事,后端诚实记录下来是这样的:

```text
对象表:
  flour_01      面粉
  sugar_01      糖粉
  egg_white_01  蛋清
  mixer_01      料理机
  mixture_01    产物(出口时创建)

事件表:
  e1  t=0     transfer: flour_01 → mixer_01 内
  e2  t=0     transfer: sugar_01 → mixer_01 内
  e3  t=5s    transfer: egg_white_01 → mixer_01 内
  e4  t=10s   process_start: mixing @ mixer_01
  e5  t=120s  transfer: butter_01 → mixer_01 内   (中途加料)
  e6  t=480s  process_end: mixing
  e7  t=480s  emit: mixture_01, derived_from {flour_01, sugar_01, egg_white_01, butter_01}

关系表(带时间区间):
  flour_01     located_in mixer_01   [0, 480]     ← 注意,不是 [0, 10]
  sugar_01     located_in mixer_01   [0, 480]
  egg_white_01 located_in mixer_01   [5, 480]
  butter_01    located_in mixer_01   [120, 480]
  flour_01     state=incorporated    [10, 480]    ← 混合开始后加的标签
  mixture_01   located_in mixer_01   [480, ...]
```

关键在这一行的设计选择:

> **原料的 `located_in` 关系一直持续到过程结束,而不是在混合开始那一刻被"杀死"。混合开始只是给它们叠加了一个状态标签 `incorporated`(已卷入/已并入)。**

为什么必须这样?三个铁的理由:

## 理由 1:中途加料逼你这么做

黄油在 t=120s 加入。如果混合开始时原料就"死了"变成了某个中间产物,那黄油加入的对象是谁?你就被迫每次加料都生成一个新的中间混合物:

```text
mixture_v1 = flour + sugar + egg_white     ← t=10 生成
mixture_v2 = mixture_v1 + butter           ← t=120 生成
```

这就是我们之前明确否决的"每个瞬间都实体化"。而如果原料关系持续存在,黄油加入就只是第 5 条 transfer 事件,和前面三条一模一样,零特殊处理。

## 理由 2:熵减魔法逼你这么做

巧克力豆混进糖粉又被挑出来。如果混合瞬间原料就消亡了,"挑出巧克力豆"在数据上就成了从虚空提取。而在"原料持续存在+标签"模型下:

```text
choc_chips_01 located_in bowl_01 [t1, t2]
choc_chips_01 state=incorporated [t_mix, t2]
e_x  t=t2  transfer: choc_chips_01 → 台面    ← 完全合法,只是加个"熵减"提示
```

## 理由 3:失败和中止逼你这么做

搅到一半停电了/主人反悔了。锅里是什么?在"原料即死"模型下是一个尴尬的半成品幽灵;在标签模型下,答案诚实而简单:**锅里是四种带着 incorporated 标签的原料,过程区间意外终止**。用户爱怎么处理怎么处理。

## 那 mixture_01 什么时候存在?

**只在出口(e7)才创建。**这就是上一轮说的"命名由引用产生"。在 [10, 480] 这段时间里,后端**没有**"面团"这个对象——只有"一组处于 incorporated 状态、位于 mixer_01 内、被一个进行中的 process 区间覆盖的原料"。

"锅里那坨东西"在过程中不是一个对象,而是一个**查询结果**:

```text
contentsOf(mixer_01, t=200) 
  = {flour_01✓, sugar_01✓, egg_white_01✓, butter_01✓} 
    + activeProcess(mixing, 已进行190s)
```

# 三、Chemist / Beaker 这类游戏是怎么做的

先说清它们的架构,再说为什么你不能照抄。

这类化学模拟游戏(Beaker、Chemist、以及大部分炼金/烹饪游戏)的典型做法是**"容器即世界"+"帧驱动重写"**:

```text
容器 = 一个化学状态向量
  contents: [{物质A, 摩尔数}, {物质B, 摩尔数}, ...]
  temperature, pressure...

每一帧(或每个 tick):
  查反应规则表 → A+B 满足条件 → 
  直接重写向量: A 减少 x, B 减少 y, C 增加 z
```

关键特征:**它们没有历史,只有现在。**倒进去的那一刻,盐酸和氢氧化钠就开始逐帧变成氯化钠和水,原料的"存在"被逐帧蚕食,直接改写。它是一个**前向模拟器(forward simulator)**——状态只能往前滚,回放?重来一遍。撤销?不存在。溯源?"这瓶氯化钠是哪次倒进去的钠反应来的"——答不出来,因为写掉了。

所以回答你的问题:**Chemist 们不是双向缓冲的,它们连单向缓冲都没有,它们是就地重写(in-place mutation)。**这对游戏完全够用,因为游戏的诉求是"此刻好玩",而你的诉求是 PLM——**历史即产品**。

你能从它们那里借的只有一样:**"容器作为反应发生地"的直觉**——东西在同一个容器里才可能互相作用。这个我们已经有了(located_in + Pile)。其余的架构对你是毒药。

一个精确的对照:

```text
Chemist:  世界 = 当前状态,      时间 = 模拟的副产品
CakeCAD:  世界 = 事件的全集,    当前状态 = 查询的副产品
```

前者是游戏引擎,后者是 event sourcing——这正是你们早就选定的路线。

# 四、回应你的"双向缓冲"猜想

你的猜想是:

> 原料从混合第一秒到最后一秒依旧存在(加标签),产物也从第一秒到最后一秒存在。

**前半句,对,而且理由如上,是被中途加料、熵减、中止三件事逼出来的必然。**

**后半句,我建议不要。**产物在过程中不存在,只在出口创建。理由:

1. **过程中它没有可陈述的属性。**t=200s 时"面团"的质量是多少?组成是什么?——等于锅内原料总和。也就是说它的一切属性都是原料的转述,一个零信息量的对象;
2. **中止时它是幽灵。**t=300s 停电,这个"存在了 290 秒的产物"怎么办?删除一个"存在过"的对象违反你们"历史不删"的公理;而原料+标签模型下,中止无需任何清理;
3. **你想要的效果不需要它。**你想要的其实是"拖播放头到 t=200 时,能看到锅里有坨正在成形的东西"——这由 `contentsOf(mixer, t)` 查询 + 3D 里一坨渐变色的 blob 就给了,不需要一个对象来背书。

所以更干净的表述不是"双向缓冲",而是:

> **原料延伸到过程终点(带标签),产物从过程终点开始。过程区间本身就是那个"缓冲"——它是唯一横跨全程的东西,承载中途事件,遮蔽内部细节。**

"缓冲"不是两份数据的重叠,而是**过程区间这个一等公民**在做的工作。

# 五、你的"热区 clip / 冷区注册表"——这次可以正式定名了

你最后那句其实已经把架构说完了,我只是把它翻译成系统词汇:

```text
你说的"热区 clip 记录操作过程"
  = 事件日志(Event Log):transfer、process_start/end、emit、measure
  = 追加式(append-only),是系统的真相来源(source of truth)

你说的"冷区 clip 记录每个时段有谁的注册表"
  = 时段注册表(Interval Registry):对象存在区间 + 关系有效区间
  = 可以从事件日志推导出来(是索引/物化视图,不是第二份真相)
```

这就是经典的 **event log + materialized index** 结构:

```text
事件日志(唯一真相,只追加)
     ↓ 推导/物化
时段注册表(为"t 时刻有谁"这类查询加速)
     ↓ 投影
Header 面板 / 3D 场景 / 召唤泳道 / 未来的任何视图
```

注意方向是单向的:**注册表永远可以从日志重建,反之不行。**所以它不是"双向缓冲"而是"单向物化"——这一点在工程上极其重要,因为它意味着注册表坏了、格式改了、想加新索引了,都可以随时从日志重算,零风险。

对黑客松,连物化都不用做:事件总量几百条,`stateAt(t)` 每次从头 fold 一遍,毫秒级。注册表这个优化,等真实项目有几万条事件时再说。

# 一、“冷区/热区”隐喻有价值，但不应该成为底层双缓冲

你的原始想法大致是：

```text
冷区：记录当前有哪些对象
热区：记录对象正在经历的过程
过程结束后，再回到冷区
```

这个认知模型很自然，但如果把它直接做成两套持久数据，就会产生问题：

- 对象在热区中是否仍属于冷区？
- 一个持续过程是否要复制全部输入对象？
- 中途加料怎么显示？
- 对象从热区“回来”是同一个对象还是新对象？
- 过程未完成时，当前内容物在哪里？
- 冷热两套表示如何同步？

因此更准确的设计是：

```text
唯一事实层
├── 对象
├── 事件
├── 关系
├── 过程区间
└── 时间

UI 投影
├── 冷视图：当前时刻注册表
└── 热视图：当前或选定时间段的活动过程
```

**冷热不是两个世界，而是同一事实的两种过滤方式。**

这样不存在真正的数据缓冲和归还：

- 对象始终在事实层；
- 过程开始后，对象进入 `参与某过程` 的关系；
- 过程结束后，该关系结束；
- 输入可能被消耗、转化或继续存在；
- 输出对象按需要创建；
- 冷视图和热视图重新投影即可。

# 二、为什么“每个事件单轨”其实比 merge 成单轨更合理？

你的直觉是对的：

> 如果热区只记录过程，为什么一定要把多个原料画成多轨，再 merge 成一条轨？为什么不让一个事件自己占一条轨？

答案是：**完全可以，而且我认为更适合 CakeCAD。**

例如混合过程无需画成：

```text
面粉 ━━━━━━━┓
糖   ━━━━━━━╋━━ 混合 ━━━ 面团
蛋清 ━━━━━━━┛
```

热区可以只显示：

```text
[10:00–10:08] 料理机混合
输入：面粉、糖、蛋清
02:00 加入黄油
05:00 加入巧克力豆
输出：曲奇面团
```

它就是一个**过程卡片/事件条**，输入输出在卡片内部折叠显示，不必占独立轨道。

如果多个过程并发，再显示多个事件条：

```text
时间 →

料理机混合    ━━━━━━━━━━━━━
烤箱预热      ━━━━━━━━━
称量巧克力豆      ━━━
```

这时每条不是“物料轨”，而是“活动过程轨”。

这有几个明显好处：

- 不需要做复杂 merge 布局；
- 不会因为输入多而纵向膨胀；
- 中途加料作为过程内事件即可；
- 原料、过程和结果的边界不需要全画出来；
- 并发关系依然可见；
- X 形交叉基本消失。

所以更准确的界面应该是：

> **当前状态用注册表/现场展示，时间变化用事件条展示。**

而不是让物料自己承担整个 DAW。

# 三、那为什么有时还需要多轨？

多轨只有在用户确实需要比较**并发和资源占用**时有意义。

例如：

```text
料理机混合
烤箱预热
黄油回温
面团冷藏
制作酱汁
```

用户要看：

- 哪些过程同时发生；
- 谁先结束；
- 哪个设备冲突；
- 哪个组件需要同时汇合。

这时多轨不是为了表现物料流，而是为了表现：

```text
活动过程
设备占用
人员占用
等待窗口
```

这就是甘特图/调度视图的职责。

换句话说：

```text
物料流图：回答“从哪来、到哪去”
事件时间线：回答“什么时候发生”
空间现场：回答“现在在哪里”
调度泳道：回答“哪些过程并行、占用什么”
```

不能指望一套线条同时回答四个问题。

因此：

> **默认用单一事件流；只有查看并发时，临时展开为多事件泳道。**

不是“多物料轨 merge 成单轨”，而是：

```text
事件列表
  ↓ 用户选择一个时间范围或并发问题
局部并发泳道
```

# 四、人脑在做菜时到底如何理解流程？

人脑的模型比较接近下面这样：

## 1. 空间工作记忆

```text
这个碗里是干料
这个锅里是酱
那边的面团正在冷藏
烤箱里有一盘东西
```

容器承担了大量信息压缩。人不会反复记：

```text
面粉、糖、盐、黄油、蛋当前分别位于哪里
```

而是记：

```text
这碗是“面糊”
```

这是**组块化（chunking）**。

## 2. 当前动作栈

```text
现在先把黄油加进去
然后打两分钟
接着加巧克力豆
```

通常只维护下一两步，不维护完整全局图。

## 3. 少量后台定时器

```text
烤箱正在预热
面团还要冷藏 20 分钟
锅里的酱偶尔要看一下
```

人的并发不是无限展开的，一般只维护少量“后台任务”。

## 4. 状态触发而非纯时间触发

```text
等鱼自然脱锅再翻
等边缘上色就出炉
等黄油软到能压动
```

人脑记录的是条件，不是完整连续状态曲线。

## 5. 目标导向的局部依赖

只有出问题或要改配方时，才会想：

```text
这碗面糊里的黄油是不是太多？
这个结果是哪个步骤造成的？
```

平时不会持续展开完整上游。

所以真人的心智模型更像：

```text
空间场景
+ 当前事件
+ 少量后台任务
+ 局部对象标签
+ 需要时召回来源
```

并不是完整 DAW，也不是设计树。

# 五、为什么把人脑模型“画出来”会混乱？

因为人脑使用了大量隐式压缩，而图形界面若全部展开，就把压缩解除了。

例如人脑说：

```text
“这碗曲奇面团”
```

实际上压缩了：

```text
面粉 300g
白糖 100g
红糖 120g
盐 3g
黄油 200g
鸡蛋 2 个
香草精 5mL
巧克力豆 180g
所有投入事件
所有混合历史
当前容器
当前温度
当前状态
```

如果 UI 把它们同时展开，当然会出现：

- 多轨；
- 汇合；
- 交叉；
- 层级嵌套；
- 线段重叠；
- 容器与物料重复出现。

因此 CakeCAD 应该也使用组块化：

```text
默认：显示“曲奇面团”
展开：显示当前组成
再展开：显示来源与投入事件
再展开：显示批次和实测
```

这不是隐藏真相，而是**按关注尺度投影真相**。

它完全不需要显示四条原料线。

# 七、“冷区”也不应是时间轨，而是当前状态注册表

冷区回答：

```text
这一刻有哪些对象？
它们在哪里？
处于什么状态？
是否正参与过程？
```

表现形式更适合：

```text

卡片
容器折叠列表
3D 场景
搜索结果

```text
当前现场 10:05

工作台
├── 巧克力豆 180g
├── 烤盘
└── 刮刀

└── 正在混合

    ├── 糖
    ├── 蛋清
    └── 黄油

烤箱
└── 预热中：162°C / 180°C
```

它不是“所有对象的时间线”，而是 `stateAt(t)` 的当前快照。

# 九、关于“单轨事件流”

如果只保留一种常驻时间结构，我建议是：

> **按发生时间排序的事件带，而不是物料轨。**

例如：

```text
09:55  烤箱开始预热
10:00  面粉、糖、盐加入料理机
10:01–10:08  料理机混合
10:03  加入黄油
10:05  加入鸡蛋
10:07  加入巧克力豆
10:08  混合停止
10:10–10:18  分团
10:20  烤盘进入烤箱
10:20–10:33  烘烤
10:33  出炉
```

这里：

- 瞬时事件是点；
- 持续事件是条；
- 同时发生时可以短暂分层；
- 默认仍是一条纵向列表或横向事件带；
- 不需要给每个物料一条轨。

这和真实人的记忆也更接近：

```text
“先发生了这些，期间又加了那个”
```

# 十一、对“产物是否从第一秒存在”的最终修正

你之前提到双向缓冲：

```text
原料全程存在
产物也全程存在
```

从 UI 角度，这可能让热区显得连续；但从事实层没必要。

推荐：

```text
过程开始前：
输入对象存在

过程中：
输入对象仍可追溯；
它们处于“参与过程/已并入”的状态；
容器内容作为动态查询结果存在；
过程本身存在。

过程结束或用户需要引用时：
输出对象获得身份。
```

UI 如果需要预览“可能的产物”，可以显示：

```text
预计输出：未命名混合物
```

但这是计划/占位符，不是已经存在的实际对象。

如果你确实想先定义输出，也可以创建：

```text
planned output
```

但必须标记为：

```text
planned / provisional
```

而不是正式成品。

# 十二、第一性答案

你的问题是：

> 真人是否真的关心时间上的多料，还是只关心空间上的多料和时间上的单线事件？

我的判断是：

> **大多数情况下，人关心空间上的多对象和时间上的少量活动，而不是时间上的所有对象。**

更准确地说：

```text
空间维度：同时存在的对象很多，用户需要看到“现在有什么、在哪里”。

时间维度：同时关注的过程很少，用户需要看到“正在做什么、还要多久、下一步是什么”。

依赖维度：平时隐藏，出问题或修改时才查看。

版本维度：平时隐藏，比较方案时才查看。
```

因此 CakeCAD 不应该默认显示完整“时空物料流”。

它应该默认显示：

```text
当前空间现场
+
单线事件时间轴
+
当前活动过程
```

然后按需召唤：

```text
并发泳道
局部来源图
分支图
物料账本
分析图
```

# 十三、最终裁决

## 保留

- 全局时间轴；
- 瞬时事件和持续事件；
- 当前对象注册表；
- 3D 当前现场；
- 当前/选中过程卡片；
- 局部并发泳道；
- 局部上/下游依赖图；
- 分支图；
- 完整事件日志。

## 砍掉

- 每个对象永久一条 DAW 轨；
- 原料必须视觉 merge 到过程再 branch 到产物；
- 冷区所有对象永久平铺；
- 为避免交叉而重塑数据结构；
- 强行在主视图中解决原料—过程—产物边界；
- 双向维护冷区和热区两套事实。

最终结构：

```text
底层：
事件日志 + 对象/关系 + 时间

默认界面：
当前空间现场 + 当前对象注册表 + 单线事件轴 + 过程卡片

按需界面：
并发泳道 + 局部依赖图 + 分支图 + 分析管道
```

一句话概括：

> **人做菜时不是在脑中维护一张全局时空物料流图，而是在空间中维护对象、在时间中维护少量活动、在需要时才追溯依赖。CakeCAD 应该沿用这种认知结构，而不是把后端所有事实同时画出来。**

# 一、为什么现在纵向时间轴变合理了？

之前如果是完整 DAW：

```text

多个过程
多个容器
多个并行分支
```

纵向时间会很难比较并发，也不符合剪辑软件习惯。

但现在已经砍成：

```text
一条主事件轴
最多 2–3 条活动轨
```

时间轴的主要职责变成：

```text
查看顺序
选择当前时刻
跳到某个步骤
查看持续区间
与 Markdown 锚点对齐
```

这些都很适合从上往下阅读。

尤其 Markdown 本身就是：

```text
从上往下写
从上往下读
```

如果时间轴紧贴 Markdown：

```text
自然语言段落 ↔ 时间事件
```

用户会很容易理解。

# 三、时间轴不是 Markdown 的行号

这一点必须注意。

不要强制：

```text
一段 Markdown = 一个时间节点
```

因为 Markdown 中可能有：

- 配方说明；
- 动机；
- 注释；
- 未来计划；
- 观察；
- 并非实际执行的假设；
- 一个段落描述多个事件；
- 多个段落描述同一个持续过程。

所以应该采用锚点关系：

```text
Markdown 片段
  ↕ 0..n
时间事件/区间
```

即：

```text
一段笔记可挂多个事件
一个事件也可挂多个笔记片段
完全没有锚点也合法
```

纵向并排只是让它们容易对齐，不应强迫其行高和时间比例完全一致。

# 四、这里有两种纵向时间轴，不要混淆

## 方案 A：文档式事件轴

事件按照顺序排列，垂直距离不代表真实时长。

```text
● 加入面粉
│
● 开始混合
│
◆ 加入黄油
│
● 停止混合
```

优点：

- 和 Markdown 对齐极好；
- 长短事件都能清楚显示；
- 页面高度可控；
- 适合自然语言过程；
- 适合只知道顺序、不知道精确时间的情况。

缺点：

- 不能直观看出“混合 8 分钟比加黄油 2 秒长多少”；
- 不适合精确拖动时间。

## 方案 B：比例式纵向时间轴

垂直距离严格对应时长：

```text
10:00 ●
      █
      █
      █ 8分钟
      █
10:08 ●
```

优点：

- 可拖动播放头；
- 时长和重叠可见；
- 接近真实时间。

缺点：

- 冷冻两小时会产生巨长空白；
- 柠檬精油存放半年无法显示；
- Markdown 很难保持对齐；
- 大量瞬时事件会挤在一起。

# 五、推荐：默认文档式，拖动时进入比例式

最适合 CakeCAD 的方式是：

> **默认纵向事件轴是非线性、文档式的；用户选择某个时间区间或进入回放模式后，再局部展开为比例式。**

默认：

```text
● 准备原料
● 混合 8 分钟
  ◆ 第 2 分钟加黄油
  ◆ 第 5 分钟加蛋
● 分团
● 冷藏 2 小时
● 烘烤 13 分钟
```

每一步占相近视觉高度，不会因为两小时冷藏把页面拉爆。

用户点击“混合 8 分钟”：

```text
局部展开
10:00 ├─────
10:02 ◆ 加黄油
10:05 ◆ 加蛋
10:08 ● 停止
```

用户点击“冷藏 2 小时”：

```text
只展开该区间
```

这叫：

```text
semantic zoom / 语义缩放
```

非常符合你对不确定时间、过程区间和 Markdown 的要求。

# 六、单轨和三轨怎么设计？

默认建议**一条主轨**：

```text
实际/主过程
```

需要时最多展开三条：

```text
轨 1：主事件
轨 2：后台过程/并发
轨 3：计划、分析或另一分支
```

例如烤曲奇：

```text
Markdown       主轨        后台轨       现场

做面糊          ●
烤箱预热        │          █ 预热
加入黄油        ◆          █
分团            ●          ● 预热完成
进烤箱          ●
烘烤            █
```

或者比较两个版本：

```text
主线：
● 直接烤
█ 13min

分支：
● 冷藏 2h
● 再烤
█ 14min
```

不要让“最多三轨”成为底层限制。底层仍可有任意并发事件；只是默认 UI 只选择最相关的三条进行显示。

# 七、纵向时间轴如何与 3D 回放结合？

在时间脊柱上有一个播放头：

```text
────●──── 当前 t
```

用户：

- 滚动文档：查看事件顺序；
- 点击事件：跳到事件开始/结束；
- 拖动持续过程内部的小播放头：查看过程中的现场；
- 使用上下键：跳到前后事件；
- Space：播放/暂停；
- 双击：局部展开精确时间；
- 右键：创建分支、添加测量、建立分析。

右侧 3D 根据 `stateAt(t)` 更新。

如果时间不精确：

```text
只知道“混合后分团”
```

点击这个事件时显示的是：

```text
逻辑时刻
```

而非绝对时钟。

因此播放头要支持两类位置：

```text
physical time：实际时间
logical position：事件顺序位置
```

# 八、它和 Markdown 对齐时，滚动谁控制谁？

不要永久强绑定滚动，否则会很难用。

建议三种模式：

## 自由滚动

Markdown 和时间轴各自滚动。

## 跟随当前锚点

点击时间事件，Markdown 滚到对应片段；点击 Markdown 锚点，时间轴滚到对应事件。

## 联动阅读

用户主动开启：

```text
锁定滚动
```

此时二者根据锚点进行近似对齐。

这更像代码与调试器、字幕与视频，而不是把两个文档强行逐行同步。

# 一、拟物还是便签?答案是:两者不冲突,但要分清谁是本体

你说的"低保真、无碰撞、可悬空、可拖拽变形的布料级拟物",我的判断:

> **要,但它的身份必须是"可变形的图标",不是"物理对象"。**

关键区分:

```text
物理引擎驱动的拟物:形状由模拟决定 → 形状是结果,用户不可直接编辑
你要的拟物:形状由用户拖拽决定 → 形状是"表达",本质是雕塑,不是模拟
```

你说的"内部拖拉拽变形表达难以穷举的空间语义"——这句话其实定义了这个东西的真实身份:

> **它是三维的自然语言。**

面皮耷拉在派盘边缘、面团被压扁、糖浆拉丝、奶油堆成尖——这些形状携带语义,就像 Markdown 里的句子携带语义。用户捏出"耷拉",系统不需要理解耷拉的力学,只需要**保存这个形状并允许日后被解释**(和自然语言注释完全同构:先记录,需要时再编译)。

所以技术选型立刻清晰了:

```text
不要:运行时布料模拟(哪怕低保真)——因为形状会不受控,悬空的布会掉,你要的"悬空但稳定"恰恰是反物理的
要:  lattice/cage 变形(FFD)+ 少量程序化 modifier
     = 每个物体套一个粗控制笼(8~27个控制点)
     = 拖控制点 → mesh 跟随变形 → 形状永久保持,绝不回弹、绝不下落
     = 想要"布料感"时,一键运行 3 秒的一次性松弛(offline relax),结果烘焙成静态形状
```

这就是 Blender 里 Lattice Modifier + 偶尔 Cloth Sim 单帧烘焙的用法,零运行时物理,视觉上却完全够"能看就行"。

**便签保留,职责不变**:便签管"说不清形状的语义"(检查气密性、轻轻拎),拟物管"说得清形状的语义"(耷拉成这样、堆成这样)。两者是同一个开放语义层的文字形态和几何形态。

## 决策 1:先定义这个软件的"不可替代内核"

从零看这个领域:烹饪/食品研发的现状是**没有 CAD、没有 PLM、没有 CAE,只有文本菜谱和老师傅的手感**。那么第一个不可替代物是什么?

不是 3D,不是仿真。是:

> **"实际发生了什么"的可追溯记录(as-built record)。**

这是 SpaceX 班底最熟的东西:火箭每次试车,最值钱的不是仿真模型,是**遥测数据和 as-built 构型记录**——这台发动机装的是哪个批次的阀门、试车时实际温度曲线是什么。仿真模型是围绕这些事实反复校准出来的。

所以内核排序:

```text
第一层(内核):事件日志 + 物料批次 + 时间 —— SpaceX 团队主导
第二层(表达):空间现场 + 可变形拟物 + 注释 —— Blender 团队主导
第三层(解释):按需分析 + 灰盒模型 + 校准 —— 三边合作
第四层(呈现):实时渲染、交互手感 —— Unreal 团队主导,但被严格限制范围
```

注意 Unreal 团队排最后且被限制——这是顾问最重要的一次说"不":**这个产品的灵魂是记录与追溯,不是沉浸感**。游戏引擎团队会不断提议"让面团real-time软化""让烤箱有真实火焰",全部砍掉,只留:高质量的静态渲染、流畅的拖拽、一次性烘焙的变形。

## 决策 2:数据架构用"航天试验数据"范式,不用"CAD 文档"范式

Autodesk 范式:一个文件=一个设计,打开、编辑、保存。
SpaceX 试验范式:**一次 campaign = 配置基线 + 事件流 + 测量流 + 分析报告**,全部 append-only。

我选后者,因为烹饪研发的真实形态就是 campaign:今天试一炉、记录、明天改参数再试一炉。对应到系统:

```text
Recipe(设计基线)     ← 版本化,像图纸
Run(一次实际执行)    ← append-only 事件流,像试车
Measurement(实测)   ← 挂在 Run 上,像遥测
Analysis(分析)      ← 引用 Run + 基线,可复算,像试后报告
```

**这一步顺便解决了你们纠结很久的分支问题**:设计分支是 Recipe 层的事(像图纸改版),执行记录根本不分支(试车没有"分支",只有一次一次的 Run),反事实分析是 Analysis 层的事(像"如果推力多 5% 会怎样"的复算)。三个概念天然分层,不再需要一个大一统的 branch 模型。

## 决策 3:几何采用"代理几何"策略,永不进入精确 CAD

Blender 团队会想做漂亮的雕塑工具,Autodesk 团队会想上 NURBS。顾问裁决:

> **所有几何都是代理(proxy):原语 + FFD 笼 + 烘焙变形。精确几何永远不做,直到 CAM(3D打印/机械臂裱花)真实出现那天,由 CAM 需求反向定义精确度。**

理由是残酷的:食品没有公差链。派盘直径差 3mm 不影响任何下游决策。花在几何精度上的每一天都是浪费。Blender 团队的真正任务是:**让"捏一个大概形状"的体验在 30 秒内完成且愉悦**——lattice 变形的手感、材质的一眼可辨、灯光的食欲感。

## 决策 4:分析引擎 = "试车台数据回归"而非"多物理场求解器"

SpaceX 实际怎么用仿真?**不是从第一性原理算出一切,而是:简化模型给方向 + 试车数据修正系数 + 下次预测更准**。这正是食品领域唯一可行的路线(数据稀缺、机理复杂、但单次实验便宜)。

所以分析引擎的架构:

```text
模型胶囊(公式/查表/小回归) + 本店 Run 数据自动校准 + 外推时诚实报告置信区间
```

砍掉:FEM、CFD、通用求解器。留一个接口,哪天真有人要算,导出到 COMSOL,别自己做。

## 决策 5:第一年只做单机单人,像早期 Blender

三个团队都会想做云、协作、平台。顾问说不:**本地文件、本地计算、开源格式**。这个领域的种子用户(高端甜点师、研发型厨师、食品极客)是个人创作者,不是企业。信任从"我的配方在我硬盘上"开始。

# 第二部分：六个新增要点

## 新增要点一：Variable 是 PLM 与 CAE 之间唯一的桥（提升为一等公民）

你在柠檬精油例子里发现"还需要有变量这个对象"，但我们没设计它。它比想象中重要得多——**它是全系统唯一能同时引用事实和模型的东西**。

```ts
type Variable = {
  id: string
  name: string                    // "oil_yield"
  
  // 三种来源之一
  binding:
    | { kind: "object_field"; ref: ObjectRef; field: string }   // flask.volume
    | { kind: "measurement"; ref: MeasurementId }               // 实测 5g
    | { kind: "expression"; expr: string; refs: VarRef[] }      // k*m*exp(-E/T)
    | { kind: "free"; prior?: Distribution }                    // 凭空声明的待拟合量
  
  // 拟合来源（描点黑盒的落点）
  fittedFrom?: RunId[]            // 从哪几次实际执行拟合出来
  fitQuality?: { r2?: number; n: number; residual?: number }
  
  // 证据与适用域
  evidence?: { doi?: string; note?: string; source: "paper"|"local_run"|"guess" }
  validDomain?: Record<string, [number, number]>
  
  unit?: string
  uncertainty?: Uncertainty
}
```

为什么它是桥：

```
PLM 侧：5g 精油是一次 Run 的实测事实，绑定柠檬皮批次
CAE 侧：5g 是 yield 表达式的一个拟合数据点
Variable：同一个 5g，两种身份，一个对象
```

这直接支撑你的"单点锚定 + 有限泛化"：第一次实验只有一个点（只能声明，不能拟合）；第二次两个点（可以插值，标记为线性假设）；换柠檬品种时 `validDomain` 越界，系统降置信而不是继续外推。

**UI 落点**：右键任何数值 → "提升为变量" → 出现在变量面板，可被表达式引用、可被后续 Run 自动喂数据。

## 新增要点二：AI Agent 作为"接线工"，这是你两张底牌的合法入口

你提过一句极关键的话：

> 仿真要不要原生交给 ai agent 来做…ai agent 很擅长处理根据标签接线。

这不只是省事，这是架构级的正确解，而且**它让你的底牌能力（受约束生成 + schema + 防幻觉）合法进入 CakeCAD，同时不碰你的平台代码**。

分工必须钉死：

```
Agent 能做：
  ① 读现场标签/关系/自然语言，提议一份 AnalysisCase（结构化 JSON）
  ② 检索适用的模型胶囊与论文参数，附来源
  ③ 把 MD 手稿里的候选对象/事件提取成待确认项
  ④ 把分析结果写成因果链报告
  ⑤ 猜测缺失参数的合理区间，并标记为 guess

Agent 绝不能做：
  ① 直接写入事实层（必须过 Zod schema + 用户确认）
  ② 修改任何 measured / executed 锁点
  ③ 自行断言物理结论（结论必须由模型算出，Agent 只解释）
  ④ 隐式补齐质量、时间、来源
```

流程：

```
用户提问（自然语言）
  → Agent 编译成 Question 对象
  → Agent 提议 AnalysisCase（拿哪些对象、哪些变量、用哪个模型、哪些是 guess）
  → 用户看 Case Preview（这里是防幻觉的关键闸门）
  → 确认后运行确定性模型
  → Agent 只负责把结构化结果翻译成人话
```

**这就是"受约束生成"的正确用法：Agent 生成的是算例，不是结论。**几何和数值全部确定性计算。答辩时这句话极硬。

## 新增要点三：外星烘烤测试（Alien Bake Test）——你哲学的极限验收标准

你说的这段是整个对话里最激进也最纯粹的表达：

> 右键烤箱新建一个"阿姆斯特朗空中转体反物质外星烘烤"，以一个乱来的时间函数，给内容物赋予乱来的"外星成熟度"指标，然后送进去处理曲奇 30 分钟，没有人会报错，下游曲奇也真的带着这个标签这个外星成熟度也不报错。

我建议把它正式化为**产品的验收测试**。任何 UI 改动、任何数据结构改动，都必须能通过这四条：

```
AT-1 可创造：用户能在 30 秒内新建一个系统从未见过的方法，无需插件、无需编程
AT-2 可传播：该方法产生的任意命名指标，能作为标签/数值挂到下游对象上并一直传下去
AT-3 零报错：全流程不弹一个错误对话框、不阻止一次保存、不要求补齐任何字段
AT-4 可分析：只有当用户要求分析它时，系统才第一次询问语义；答不出来就诚实返回 unknown
```

它对应的实现要求非常具体：

```ts
// 方法不是类，是数据
type MethodDef = {
  id: string
  name: string                      // 用户随便起
  appliesTo?: string[]              // 可留空（万物皆可）
  emits?: IndicatorDef[]            // 自定义指标，任意命名、任意单位
  timeFunction?: string             // 任意表达式，可以是乱来的
  builtin: false                    // 用户自造
}

type IndicatorDef = {
  name: string                      // "外星成熟度"
  unit?: string                     // 可以是 "喵" 
  semantics?: null                  // 就是 null，且这完全合法
}
```

`semantics: null` 是这个测试的灵魂：**系统必须能存储和传播它完全不理解的东西。**

## 新增要点四：3D 的诚实裁决与降级预案

你的质疑必须被正面回答，而不是绕过。

**判断**：3D 在四件事上不可替代，其余全是装饰。

```
① 表达难以言说的空间语义（贴派盘、包惠灵顿、火鸡填充、装置装配）
② 剖面理解（多层甜点、牛排熟度梯度、面包组织）
③ 空间基准操作（沿派盘边缘修边、以容器为参照）
④ 一眼可辨的现场感（回放时"哪些东西在哪里"的瞬时认知）
```

反过来，3D 在这些事上是负担：混合过程内部、配方比例、时间调度、物料账本、溯源链——这些用表格和列表更好。

**所以裁决**：3D 是"空间投影视图"，不是主视图。它和 Header、时间脊柱平级。

**降级预案（必须现在就设计好）**：如果用户验证证明 3D 是自我感动，系统砍掉 3D 后必须仍然完整。检验方法：

```
把 3D 视口整个隐藏，问：
  - 事件日志还完整吗？→ 是
  - PLM 溯源还工作吗？→ 是
  - 分析还能跑吗？→ 是（几何参数退化为数值字段：厚度/直径/层数）
  - Markdown + 时间脊柱 + Header 还能记录整个曲奇流程吗？→ 是
```

只要这四问全是"是"，3D 就是安全的赌注——**赢了是差异化，输了删掉一个文件夹。**

**建模资产的裁决（你问过厨师机怎么建模）**：全部用原语 + 标签牌 + 可选照片贴图。

```
碗       = 半球壳
料理机   = 圆柱 + 顶部标签牌 + 可选正面贴图
烤箱     = 盒子 + 门线 + 标签
面粉堆   = 扁球（Pile）
液体     = 半透明凸包
面团/面皮 = 可 FFD 变形的板/块
设备内部 = 不建模，用 Stub 表达
```

规则：**任何单个资产超过 15 分钟制作时间，就改用原语+贴图。**照片贴图完全可以接受——它诚实地说"这里有一台料理机"，而不假装建模。

## 新增要点五：操作手册导出——你无意中发现的杀手功能

你写那 20 多个 bench 情景时，用的形式是"给完全没有生活经验的外星机器人的操作手册"。**这不是巧合，这揭示了 CakeCAD 的天然输出物。**

```
一次 Run 的完整记录
      ↓ 导出
一份可执行的操作手册
（步骤、时序、条件、禁止项、注意事项、实测值、物料清单、设备清单）
```

它的四重价值：

**① 杀手 Demo**：录完一次曲奇，一键导出 PDF/Markdown 手册。评委立刻懂了产品价值——这是别人做不到的，因为别人没有结构化记录。

**② 完备性反向验证**：如果导出的手册无法让另一个人复现，说明记录缺了东西。这是比任何单元测试更强的验收标准。你自己写的那些手册就是"目标输出"的黄金样本。

**③ 通往 CAM 的天然桥**：给人执行的手册，就是给人执行的 CAM 计划。将来给机械臂的路径只是同一份计划的另一种编译目标。

**④ 真实商业价值**：餐厅 SOP、连锁标准化、新人培训、代工交付文件、研发交接。这可能比仿真更早产生收入。

导出应支持多个目标：

```
详细手册     — 每步都写，给新手/外星机器人
简明手册     — 老手用，只写关键点和条件
清单模式     — 物料 BOM + 设备清单 + 时序甘特
研发报告     — 版本对比 + 实测 + 分析结论 + 未解决问题
```

## 新增要点六：七种"不知道"必须各自有表示

你的"未知合法"是核心哲学，但 unknown 不是一个东西。混在一起会让系统无法给出有用提示。

| 类型 | 例子 | 数据表示 | 下游行为 |
|---|---|---|---|
| 值未知 | 挤了多少奶油 | `value: null, knowable: true` | 可补测；灰点提示"可测量" |
| 存在未知 | 碗壁还有残留吗 | 候选对象，`confidence: low` | 只影响守恒审计 |
| 时间未知 | 什么时候分的团 | `order-only` 约束 | 排程分析拒绝运行，其余照常 |
| 因果未知 | 为什么这两个摊开了 | Question 未解决 | 触发后验诊断 |
| 适用性未知 | 这模型能用于此配方吗 | `validDomain` 越界 | 降置信，标记外推 |
| 身份未知 | 这是昨天那碗吗 | 弱绑定关系 | 溯源链标"断点" |
| 原则不可知 | 杏仁粉的"真实完整物性" | `semantics: null` | 每个分析各自声明材料视图 |

最后一类是你亲自指出的（"完整定义是个伪命题"）。它的表示方式最重要：**不是留空等着被填，而是明确记录"此处不存在唯一答案，各分析自行假设"**。UI 上它不是警告，是一个中性图标。

# CakeCAD 设计总文档 v1.0

## 1. 产品定义

> **CakeCAD 是一个本机优先的过程研发工作台。它以时间为坐标系，记录物料、工具、设备与中间体如何出现、移动、组合、分离与演化；用户可以用自然语言、空间操作和可变形几何自由表达难以穷举的现实操作，而无需预先服从任何完整的工艺本体。系统只维护最小的诚实事实（身份、时间、关系、数量、来源），并在用户要求追溯、执行、比较、分析或制造时，才把相关局部编译成用途特定的表示。**

一句话哲学：

> **自由地摆，诚实地记，按需绑定，局部地算。**

三句话解释给外行：

```
菜谱软件记录你打算做什么。
CakeCAD 记录你的厨房里实际发生了什么。
做出来之前不必定义，算得动的时候才要求严格。
```

## 2. 定位边界

### 是什么

```
过程研发的记录、追溯、比较与局部分析工具
面向个人创作者与小型研发团队
本地文件、本地计算、可选云端 AI
以食品为切入点，抽象适用于实验室/工坊/小批量制造
```

### 不是什么

```
不是做菜游戏（食材没有预设命运）
不是强约束 CAD（不要求先定义后操作）
不是通用物理引擎（不做运行时模拟）
不是通用 CAE（不做网格与多物理场）
不是 SaaS 协作平台（第一年单机单人）
不是菜谱社区（不做内容分发）
不是通用节点平台（内部有 DAG，但不暴露为任意工作流编辑器）
```

## 3. 十二条产品公理

```
A1  食材、工具、容器、设备均无预设命运
A2  未知合法：不定义不算错，不阻止编辑
A3  历史不删：已执行、已测量的事实不可被模型或设计改写
A4  空间操作默认不产生物料事实，需确认或被分析需求提升
A5  命名由引用产生：只有要用它时，它才需要身份
A6  操作自由，仿真诚实：可以做任何事，但不能对模型说谎
A7  局部闭合优于全局闭合：只让当前任务相关的部分严格
A8  一切视图皆廉价投影，前端布局问题不得反向修改数据结构
A9  几何精度由下游需求定义，无需求即代理几何
A10 分析针对问题建立临时解释，不维护完整世界模型
A11 每个数值必须携带来源与地位（用户/实测/派生/预测）
A12 通过外星烘烤测试：能创造、能传播、零报错、按需分析
```

## 4. 三层骨架：Recipe / Run / Analysis

这是消解分支难题的关键结构。

```
┌──────────────────────────────────────────────┐
│ Recipe（设计基线）                            │
│   可版本、可分支、可 diff、可 merge            │
│   包含：意图、参数、结构、Markdown 底稿        │
│   像图纸                                      │
└───────────────────┬──────────────────────────┘
                    │ 实例化
┌───────────────────▼──────────────────────────┐
│ Run（一次实际执行）                            │
│   append-only 事件流，永不分支                 │
│   包含：事件、实测、观察、中止、介入            │
│   像一次试车                                  │
└───────────────────┬──────────────────────────┘
                    │ 引用
┌───────────────────▼──────────────────────────┐
│ Analysis（分析与情景）                         │
│   引用 Recipe + Run，可复算，可沙盒            │
│   输出区间/分布/情景，不冒充事实               │
│   像试后报告与反事实推演                       │
└──────────────────────────────────────────────┘
```

### 为什么这样切

你之前的困惑与本结构的对应解：

| 原困惑 | 三层结构下的解 |
|---|---|
| 分支要不要同步上游 | Recipe 层的普通版本 diff/merge，成熟问题 |
| 分支能否给具体值 | Analysis 只给分布与情景样本，不给伪事实 |
| 破坏性仿真怎么隔离 | Analysis 天然是沙盒，不触碰 Run |
| 实测被模型覆盖怎么办 | Run 的实测是 append-only，Analysis 无写权限 |
| 分支要不要用户选类型 | 不需要。Recipe 分支=设计；Analysis 情景=推演；Run 不分支 |
| 备份怎么做 | Recipe 快照 + Run 归档，都是天然不可变 |

### Run 的特殊规则

```
Run 只能追加，不能修改历史事件
Run 可以被中止（aborted），中止即事实，不清理
Run 可以有人工介入事件（intervention）
Run 结束后仍可追加实测与观察（后验回填）
Run 之间可以对比（先煎后烤 vs 先烤后煎 = 两个 Run）
Run 不分支——改主意就是一次新的 Run 或一次中止
```

```ts
type CombineMode =
  | "mix"          // 产生新对象，输入失去独立身份

### 5.6 锁点

```ts
type LockType =
  | "user_fixed"        // 我就是要 1000g
  | "measured"          // 实际称出来 487g
  | "executed"          // 已经做完的，设计改动不能重写
  | "imported"          // 来自温度计/秤/打印机

锁点的语义是：**自动传播不能越过的边界**。用户手动仍可修改，但会产生显式冲突记录。

## 6. 视图体系

### 6.1 视图公理

```
事实层唯一，视图皆廉价投影
视图不得反向修改数据结构（A8）
视图可以有很多个，可以随时丢弃
可写视图越少越好
```

### 6.2 五个视图

| 视图 | 回答的问题 | 可写 | 默认状态 |
|---|---|---|---|
| Markdown 底稿 | 我在想什么、为什么 | 是 | 可折叠侧栏 |
| 时间脊柱 | 顺序、持续、当前在哪 | 半（可点选、拖播放头） | 常驻，窄 |
| 3D 现场 | 此刻东西在哪、什么形状 | 是（拖放、FFD） | 主体 |
| Header 状态 | 此刻正在发生什么 | 否 | 常驻，一条带 |
| 召唤视图 | 并发/来源/分支/账本 | 否 | 高度 0，按需 |

### 6.3 主布局

```
┌──────────┬──────┬────────────────────────┬───────────┐
│ Markdown │ 时间 │      3D 现场            │ Inspector │
│ 底稿      │ 脊柱 │                        │           │

## 7. 3D 现场

### 7.1 资产策略

```
一切用原语 + 标签牌 + 可选照片贴图
单个资产制作超过 15 分钟 → 改用原语
```

```
碗       半球壳
料理机   圆柱 + 顶部标签 + 正面贴图
烤箱     盒子 + 门线 + 标签
面粉堆   扁球（Pile）
液体     半透明凸包
面团/面皮 可 FFD 变形的板/块
装置     原语组合 + 连接线
设备内部 不建模，用 Stub
```

### 7.2 FFD 变形：三维便签

```ts
type ProxyGeometry = {
  primitive: "box" | "cylinder" | "sphere" | "halfSphere"
           | "slab" | "blob" | "extrude"
  params: Record<string, number>

  lattice?: {
    resolution: [number, number, number]     // 通常 3×3×3 或 2×2×2
    controlPoints: Vec3[]                    // 用户拖出来的形状
  }

  bakedMesh?: string          // 一次性松弛/布料模拟的烘焙结果
  semanticNote?: string       // "耷拉在派盘边缘"
}
```

**绝对规则：**

```
零运行时物理
形状由控制点决定，永久保持，不回弹、不下落
悬空、穿模、体积不守恒全部合法
想要布料感 → 一次性 3 秒松弛 → 烘焙成静态形状
```

### 7.3 特殊原语

**Region（区域）**：画个框，打个标签，不参与物料流。台面、备料区、仓库区。需要时才升级为对象。

**Pile（散堆）**：位置化的物料聚集，无壁无容量。台面上两坨互不干扰。

**Stub（存根）**：声明存在但不展开建模。

```
隔空冷凝水  = 供给 stub + 粒子流效果
物理悬空    = 支撑 stub（"我知道该有个架子"）
派盘刷油    = 界面 stub
烤箱预热好  = 环境 stub
```

Stub 三态：纯视觉 → 已声明（参数未填）→ 仿真时赋值。

**空间便签**：3D 里的浮空文字，有空间锚点 + 时间区间。

```
"检查气密性"  锚定冷凝管上方  持续 20s
"轻轻往里拎，不要捏"  锚定派皮边缘
```

## 8. 分析系统

### 8.1 五维分类矩阵

不要把这些混成一维。

```
维度1 对象：object / process / history / scenario
维度2 时间：static / dynamic
维度3 方向：predictive / diagnostic
维度4 重量：quick_estimate / local_analysis / heavy_solver
维度5 破坏：read_only / non_destructive / destructive
```

例：

```
烘烤中心温度      process·dynamic·predictive·local·read_only
成品厚度检查      object·static·diagnostic·quick·read_only
提前5分钟出锅     scenario·dynamic·predictive·local·sandbox
重分配质量以求解  process·dynamic·predictive·local·destructive→沙盒
```

### 8.2 Question 作为一等对象

分析从提问开始，不从按钮开始。

```ts
type Question = {
  id: QuestionId
  text: string                 // 用户原话
  target: ObjectRef[]
  timeScope?: TimeRange
  mode: "estimate" | "diagnose" | "scenario" | "check" | "optimize"
  intervention?: Record<string, unknown>    // 反事实的假设修改
  requestedOutput?: string[]
  status: "open" | "answered" | "unanswerable"
  answers?: AnalysisResultId[]
}
```

### 8.3 模型胶囊

```ts
type ModelCapsule = {
  id: string
  name: string
  question: string[]                      // 能回答什么

  applicability: {
    materials?: Matcher[]
    process?: Matcher[]
    ranges?: Record<string, [number, number]>
    exclusions?: string[]
  }

  inputs: VarSpec[]
  outputs: VarSpec[]

  form:
    | { kind: "formula"; expr: string }
    | { kind: "lookup"; table: string }
    | { kind: "regression"; artifact: string }
    | { kind: "state_machine"; states: string[]; transitions: Transition[] }
    | { kind: "fd_1d"; scheme: string }     // 一维有限差分（传热）
    | { kind: "rule"; rules: Rule[] }
    | { kind: "external"; adapter: string }  // COMSOL/Simulink 导出

  evidence: { doi?: string; n?: number; validation?: string; rmse?: number }
  extrapolation: { allowed: "none"|"limited"|"free"; maxDistance?: number }
  cost: { latency_ms: number; requiredMeasurements: string[] }
}
```

### 8.4 三种融合，不做加权平均

```
A  机理基线 + 数据修正残差    ŷ = y_physics + r_data(x)     ← 最适合
B  机理生成特征 + 小模型预测   features → classifier
C  多专家 + 规则门控          按适用域/样本距离选择
```

必须分开显示两个数：

```
结果不确定度：失败概率 30%–55%
模型适用可信度：低（跨配方外推）
```

### 8.5 五级置信

```
Verified      本配方本设备实测域内
Supported     有相邻实验或可靠机理
Extrapolated  有限外推
Speculative   仅趋势或弱先验
Unknown       拒绝预测
```

`Unknown` 是合法答案，不是失败。

### 8.6 Case Preview：防幻觉闸门

**任何分析运行前必须显示：**

```
本次分析将使用：
  ✓ 面团几何（12团，平均直径估算 45mm）
  ✓ 烤盘几何
  ✓ 烤箱设定 180°C
  ✓ 黄油状态：偏软（用户观察）
  ? 面团质量：3团未称重，用平均值代入
  ? 油层厚度：未知，假设为 0

将忽略：
  刮刀 · 油纸皱褶 · 操作手势 · MD 中的未确认段落

模型：cookie_spread_empirical_v1
  依据：2 次本店 Run + 1 篇文献
  适用域：黄油 15–25%，当前 22% ✓
```

用户可以补参数、改假设、接受默认、跳过未知、取消。

### 8.7 破坏性判定

```
只读（读取事实，返回结果）             → 不建沙盒
非破坏（临时补参数，不写事实）          → 不建沙盒
破坏性（重分配质量/改状态/跨越离散/
        需要闭合守恒/需要网格化预处理） → 建 Analysis 沙盒
```

沙盒是 Analysis 层的属性，不是用户要选的分支类型。

### 8.8 廉价的诚实层（沉默审计）

三条公理，永远在跑，成本约等于零，默认不说话。

```
公理1 接触留痕
  任何对象进入粘性物/液体范围又离开
  → 生成 possibly_contacted 候选关系
  → 默认完全沉默，对象上一个极小灰点
  → 点开：[确认无转移] [声明沾附] [忽略]

公理2 质量账本永远在记
  每个混合物随时有：理论输入 vs 已声明输出
  差额不报错，永远可查

公理3 拓扑最低检查
  引用不存在的对象      → 硬错误（唯一的硬错误）
  产物早于全部原料      → 黄色标记
```

这解决了"漏了也发现不了"：**漏掉的东西全留了痕，只是默认不吵你。**

### 8.9 熵减魔法

```
事前混合 + 按比例倒出      正常，仿真可用混合态
事前混合 + 单组分抽出      ⚠提示但不阻止，剩余组成重算
事前未混合 + 单组分取出    连提示都不用
事前未混合 + 想按混合态仿真 ← 唯一需要拦的：朝仿真说谎
```

原则：**操作自由，仿真诚实。**

## 9. AI Agent

### 9.1 边界

```
能做
  ① 读现场标签/关系/自然语言，提议 AnalysisCase
  ② 检索模型胶囊与文献参数，附来源
  ③ 从 MD 手稿提取候选对象/事件（待确认）
  ④ 把结构化结果写成因果链报告
  ⑤ 猜测缺失参数区间，标记为 guess
  ⑥ 根据标签"接线"（这是它最擅长的）

绝不能做
  ① 直接写事实层（必须过 Zod + 用户确认）
  ② 修改 measured / executed 锁点
  ③ 自行断言物理结论
  ④ 隐式补齐质量、时间、来源
  ⑤ 静默修改配方或历史
```

### 9.2 流程

```
自然语言提问
  → Agent 编译成 Question（结构化）
  → Agent 提议 AnalysisCase
  → Case Preview（防幻觉闸门）
  → 用户确认
  → 确定性模型计算
  → Agent 把结果翻译成人话 + 因果链
```

**Agent 生成算例，不生成结论。**几何和数值全部确定性计算。

### 9.3 离线可用

```
无网络时仍可：打开项目、编辑几何、记录事件、
              物料计算、跑本地模型、导出手册
Agent 是增强，不是依赖
```

## 10. 操作手册导出

### 10.1 为什么是杀手功能

```
① 演示：一键从 Run 导出手册，评委立刻懂
② 验收：手册不能让别人复现 → 记录缺东西
③ 通往 CAM：给人的手册 = 给机器的计划的前身
④ 商业价值：SOP、培训、连锁标准化、代工交付
```

### 10.2 四种目标

```
详细手册   每步都写，给新手（你写的 bench 情景就是黄金样本）
简明手册   只写关键点与条件判据
清单模式   BOM + 设备清单 + 时序甘特
研发报告   版本对比 + 实测 + 分析结论 + 未解决问题
```

### 10.3 手册必须包含的元素

从你写的 bench 情景反推：

```
对谁、用什么、做什么
前置条件（"等外壳形成"）
完成判据（"边缘上色，中心未硬"）
禁止项（"鱼仍粘锅时不得强行铲"）
等待类型（固定/条件/资源/同步）
实测值与理论值
Stub 提示（"此处需要支架"）
安全注意（危险温区、设备安全）
未知项（诚实标出"此处凭判断"）
```

## 14. 十天黑客松执行计划

### 环 1：事实内核（Day 1–2）

```
Object / Event / Relation / TimeRange / ValueCell

无 UI 也能跑。这是唯一不可省的东西。

```
纵向语义时间轴，可点选可拖播放头

悬空警告（顺手做，本来就是状态倾倒的一部分）
双击局部展开为比例时间
```

做完这一环，已经是个 Braker/Chemist 式产品了。

### 环 3：3D 现场（Day 4–6）

```
R3F + 原语资产（碗/料理机/烤箱/面粉堆/面团）
拖入拖动 → 空间事件
FFD 笼变形（3×3×3）
Region / Pile / Stub / 空间便签
选中高亮 + 头顶标签
```

不做建模，不做物理，不做碰撞。

### 环 4：曲奇全流程 + 一个分析（Day 7–8）

```
1  MD 写三行笔记
2  拖出原料 → 3D 摆放
3  多选右键"混合" → 时间脊柱出现过程区间
4  拖播放头过程中 → Header 显示"料理机运转中"
5  过程结束 → 自动生成 mixture_01 → 重命名"曲奇面团"
6  分 6 份 → 摆烤盘 → 进烤箱
7  点"快速估算" → Case Preview → 返回观察窗口区间
8  按 T 召唤泳道：烤箱 vs 面团 重叠对照
9  回填实测："13分钟，出炉 80g" → 显示理论/实测差异
10 一键导出操作手册
```

第 7 步的模型可以是写死的经验公式，重点是展示"按需分析 + 区间输出 + 诚实未知"的姿态。

### Day 9：加分环（按性价比排序，挑一个）

# 一、软件开发"对着什么"开发：六种路数

先给结论：**没有一种路数适用于所有项目，选错路数比写错代码致命得多。**

## 路数 1：对着界面开发（Design-Driven / Mockup-Driven）

```
高保真设计稿 → 拆组件 → 补后端 → 上线
```

**适用**：形态已知的产品。做第 500 个待办清单、第 200 个电商 App。前人已经把交互范式验证过了，你只要做得更好看更快。

**致命处**：如果形态未知，界面会**反向决定数据结构**。你已经亲身撞过这个坑——DAW 视图逼你去解决"默认容器归属""X 形交叉"这些伪问题。那一刻你其实在无意识地走"对着界面开发"，然后自己察觉不对，砍掉了。**那次砍是这整个对话里最有价值的判断。**

## 路数 2：对着 UML / 模型开发（Model-Driven）

```
领域类图 → 时序图 → 状态机 → 生成骨架 → 填实现
```

**适用**：领域已被前人形式化过的地方。银行账务、保险理赔、订单流转、编译器。这些领域的本体（entity 和它们的关系）几十年前就稳定了。

**致命处**：**UML 假设本体先于实现存在**。你的领域恰恰相反——你花了整场对话证明"烹饪操作语义无法预先穷举"。如果一开始画 UML，你会画出 `BakeOperation`、`WrapOperation`、`FillOperation`……然后在第 7 个 bench 情景（惠灵顿）时全部推翻。

而且注意：**我在这次对话中就犯过这个错**。第 4 版我推的"严格 IR + 操作语义集"本质是 model-driven 思路，被你的 bench 情景否掉了。

## 路数 3：对着 PRD 文档开发（Spec-Driven / Waterfall）

```
需求文档 → 评审 → 设计文档 → 开发 → 验收
```

**适用**：需求来自外部权威且不可协商。航天、医疗设备、政府系统、GxP 合规软件。这些领域"文档本身就是交付物"，而且需求真的稳定。

**致命处**：你自己说了——"一篇篇纠缠的不正交的 PRD"。这是必然的，因为**自然语言无法保持正交**。两份 PRD 各自合理，合起来矛盾，而矛盾要到实现时才暴露。

## 路数 4：对着测试开发（TDD / Spec-by-Example）

```
写一个失败的测试 → 让它通过 → 重构 → 循环
```

**适用**：行为可判定的地方。算法、解析器、状态机、金融计算。

**致命处**：TDD 要求你**先知道正确答案**。"面糊什么时候开始是面糊"没有正确答案，写不出测试。TDD 在你的核心难题上完全失效——但注意，它在**事实内核层**完全适用（`stateAt(events, t)` 就该 TDD）。

## 路数 5：对着场景开发（Scenario-Driven / Use-Case-Driven）

```
收集大量真实场景 → 归纳共性 → 提炼抽象 → 实现 → 用新场景回测
```

**适用**：领域开放、本体未知、需要被发现而非被规定的地方。

**这就是你正在走的路数，而且你走得非常标准。**下一节详说。

## 路数 6：对着数据流开发（Data-Flow-Driven / Event-First）

```
先定义"世界上会发生什么事件" → 事件如何改变状态 → 状态如何投影成视图
```

**适用**：过程即产品的领域。金融交易、日志系统、游戏回放、CI/CD、以及**你的领域**。

**这是你最终收敛到的架构路数**（事件日志为真相源），和路数 5 是搭配关系：场景驱动帮你发现"有哪些事件"，事件驱动帮你组织"如何存储和投影"。

# 二、你的核心猜想：bench 单点突入 → 逆向找正交

**你的猜想是对的，而且这个方法有正式名字。**

## 它叫什么

这是**Grounded Theory（扎根理论）**在软件工程里的形态，工程界的具体名称包括：

```
Specification by Example       用例说明规格
Scenario-Driven Design         场景驱动设计
Bottom-Up Domain Discovery     自下而上的领域发现
Extreme Characterization       极端特征化（故意挑最难的样本）
```

数学上它是**用样本反推基（basis）**：

```
20 个蛋糕 = 20 个样本向量
你要找的 5 个三级菜单 = 能张成这 20 个向量的基
```

## 你说"20 个逆向得到 5 个菜单，比 2000 个一个个试好"——对，但要加两个条件

### 条件 1：样本必须是极端点，不是随机点

如果 20 个蛋糕都是"圆形海绵蛋糕加奶油"，你逆向出的抽象是废的。必须挑**互相正交的极端**。

**看你实际挑的样本：**

```
派盘修边      → 工具基准不是标准配置
悬空冷凝管    → 建模可以不完整（Stub）
外星烘烤      → 语义可以不存在
熵减抽巧克力  → 混合可逆
分蛋污染      → 质量守恒≠可用
巧克力调温    → 状态有隐藏历史
牡蛎缎带面    → 过程可并发
酵种          → 对象跨项目
炸油          → 介质会老化
```

**你不是在采样，你是在做极端特征化。**每一个样本都是为了杀死一个特定假设而选的。这就是为什么 26 个情景抵得上 2000 个：它们几乎互相正交。

一个诚实的检验：如果我给你第 27 个情景"做戚风蛋糕"，它大概率**不会产生新概念**——因为它落在你已张成的空间内。这恰好证明你的基已经接近完整。

### 条件 2：逆向出来的必须是"关系与机制"，不是"分类"

这是最容易出错的地方，也是我第 4 版失败的原因。

```
错误的逆向（我犯的错）：
  20 个蛋糕 → 归纳出 15 种操作类型 → BakeOp, MixOp, WrapOp...
  结果：第 21 个蛋糕就要加第 16 种

正确的逆向（你做的）：
  20 个蛋糕 → 归纳出 6 种物质基础操作 + 若干关系类型 + 开放语义槽
  结果：第 21 个蛋糕用现有的组合就能表达
```

判定标准很硬：

> **如果新样本需要新增"类型"，你的抽象错了。如果新样本只需要新增"实例/组合/标签"，你的抽象对了。**

你的最终内核（create/transfer/combine/separate/place/process + 关系 + 开放标签）通过了这个检验。

## 但这个方法有一个真实的失败模式

**你可能已经在里面了**，我必须指出来：

```
过度逆向（over-abstraction）：
  样本继续增加 → 抽象继续上升 → 最后抽象到"对象、事件、关系、时间"
  ↑ 这是元本体，适用于一切，因此对任何具体事物都没有帮助
```

**症状检查**（你自己判断）：

- 你的最终内核是 `Object / Event / Relation / Time` ——这**同时是**烹饪的抽象、化学的抽象、制造的抽象、和一切过程的抽象；
- 你的公理"食材没有预设命运"——正确，但它同时也是"任何东西都没有预设命运"；
- 你说过"CakeCAD 最后可能长成某种研发和 PLM 的巨兽"。

这不是说抽象错了。**抽象是对的，但抽象本身不构成产品。**Git 的抽象是"内容寻址的有向图"，但 Git 之所以成功不是因为这个抽象，是因为它把 `branch`、`commit`、`merge` 这三个具体动作做到了肌肉记忆级别。

所以你的下一步不是继续逆向，是**正向**：

> **从张成的空间里，挑出 5–7 个具体的、有手感的、可肌肉记忆的操作，把它们做到极致。**

# 五、回答你最初的问题

> 软件开发究竟是"对着什么"开发呢？

**答：对着"用户重复最多的那 5–7 个动作"开发。**

界面、UML、PRD、测试、场景、事件流——全都是工具，用来发现和验证这 5–7 个动作。它们本身不是开发对象。

判定标准：

```
如果你能说出"用户一天会做这个动作 50 次" → 这是开发对象
如果你只能说"系统需要支持这个能力" → 这是需求，不是开发对象
```

Git 的核心是 `add / commit / push / branch / merge / rebase`——六个。
Figma 的核心是 `选 / 移 / 缩 / 组 / 复制 / 建组件`——六个。
Blender 的核心是 `选 / 移 / 挤出 / 循环切 / 修改器 / 渲染`——六个。

**你现在有了完整的世界观和骨架，缺的是那六到七个手势的精确定义。**这也解释了你的直觉"这个项目经常因为生活化的细枝末节挡路"——那些"细枝末节"就是手势，它们挡路是因为它们才是真正的产品。

要不要我们下一步就把这七个手势的脚本逐一写出来？那是 Day 1 上午真正要用的东西，比任何数据结构定义都更早需要。
